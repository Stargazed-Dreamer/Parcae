# temp 文件夹清理 (temp_cleanup)

## 触发词
整理temp、清理temp、temp清理、临时文件整理、temp太乱、清理临时文件、temp cleanup、temp整理

## 概述

`temp/` 是临时堆积区：`exec_python` 的临时脚本、调试日志、终端会话日志、一次性任务的中间数据、临时解压内容都落在这里。它的本质是**内容随任务流动**——目录名每隔几周就换一批，而"这东西删了能不能找回来"这个性质是稳定的。

**本 skill 的核心方法：按性质判定，不按名字查表。** 而"性质"只能从**实际读过的内容**得出——没读过内容的文件，不具备被判定为"可删"的资格。

> 历史上本 skill 曾用 A–M 十三类"目录名 → 处理方式"决策表，2026-08-28 实测 13 类里 11 类的名字已不存在 ⇒ 改为三问。

## 零、清理目标：三个指标，缺一不算完成

| 指标 | 压它为了解决什么 | 实测反例（2026-10-22） |
|---|---|---|
| **体积** | 磁盘占用 | — |
| **条目数** | 「看着乱」的直接来源 | 删 51 项 / 4.97 GB，体积 −78%，**条目数 750 → 708 只 −6%** |
| **混乱度** | 说不出归属的条目占比 | 剩 709 项里 **670 项 <1 MB，只占 1.6% 体积却占 94.5% 条目** |

⛔ **体积不是条目数的代理。** 只按体积排序清 Top-N，条目数几乎不动——因为长尾散文件体积小、数量大。
⛔ **条目数也不是体积的代理。** 清掉 670 个散文件只回收 24.5 MB。两个指标必须分别设目标、分别验收。

**验收标准**：清理后 `temp/` 下每一项都能一句话说出「它属于哪个任务 / 为什么要留」。
说不出来 ⇒ 要么归位（Step 5）、要么进删除清单，**不许留在原地当"待定"**。

### 关于空间释放（条件句，⛔ 不要默认执行）

- 送回收站 **不释放**同盘空间——文件只是挪进 `$Recycle.Bin`，字节还在。
- **只有用户明确说要腾空间时**，才做第二步 `recycle_audit.py` 确认入站 → `recycle_purge.py --entry ID=原路径 --yes`。
- 用户说「清理一下 temp」「整理 temp」= **去乱**，不是要空间。别自作主张补永久删。
- 与全局规矩「只删到回收站、永久删由用户清」是**串联关系，不是二选一**：
  前者管「怎么删」（可逆缓冲 + 入站校验，防的是**路径写错**——写错了回收站里根本没这条，purge 就不会执行）；
  后者管「要不要再释放空间」。两者互补，不冲突。
  ⚠ 曾把这两条当互斥去问用户，被当场纠正（2026-10-22）。

## 一、三问决策树

对 `temp/` 下每一项（先按**顶层目录**判定，再按需下钻）依次问：

```
（前置：先按本节末"判可删前必须读过内容"读过这个文件，再往下问）
Q1 可重建吗？（删掉后能否重新生成 / 重新获取——必须实际验证重放路径现在还能跑通）
   是 → ✅ 可删【回收站】
   否 ↓
Q2 是唯一副本吗？（世上还有别处存着吗）
   是 → ★ 保护（绝不删；可提议移动，由用户定）
   否 ↓
Q3 有归属吗？（属于某个 workspace 任务、别的项目、或某个已登记的仓库对象）
   有 → 📦 移回归属地（不删、不留在 temp）
   无 → ❓ 标"待定"，交用户裁决
```

三问之外还有第二节的交叉校验，**任何判定都要再过一遍**。

### 前置：判"可删"之前必须真的读过这个文件

**对每一个准备列入删除清单的文件，必须先实际读取其内容至少 30 行（不足 30 行则读全文；大文件读开头 30 行 + 结尾 30 行），读到内容才能落判定。仅凭文件名 / 扩展名 / 目录名 / 体积下结论一律无效。**

- **"看起来像可复现产物"不等于可复现**：Q1 判"可重建"之前，必须验证重放路径**现在真的还能跑通**（生成脚本还在、上游数据还在、对应代码版本没变）。跑不通就是一去不回的历史记录。
- **来历不明的文件先读它自己会说话**：打开文件头几十行通常能看到时间戳、生成命令、"本报告由 xxx 生成"之类的自述，比猜目录名可靠得多。读不出来历的文件按 Q2/Q3 处理（保护或待定），不要按名字归类。
- 代价已实测过一次：2026-08-30 把 `temp/audit/final_report.md`（23 KB）与 `pyright_summary.md`（8.8 KB）按文件名当"可复现产物"删除，实际是一次性历史审查记录、被文档引用 5 处、且对应代码版本已变更无法重放。

**目录级 / 批次级的批量判定不允许跳过这一条**：想整份删一个目录或一整批，先抽样（见第六节）真读内容，抽样发现任何"唯一副本 / 被引用 / 不可复现"信号，就停止批量判定，逐文件过。

## 二、交叉校验（判定之后必须再过一遍）

### 1. 活跃性 → 一律保留，不得入删除清单

命中任一条即保留：

- **mtime 在最近 2 小时内**（2026-08-30 实测：清理进行中 temp 就被并发会话写入两次。窗口再小就会端掉别的会话几分钟前刚生成的文件）
- **WIP 关联**：`wip_list` 查 DB 中的 open 任务（真源），并 grep `.agents/wip/*.md`（人类可读留档）——两边都无关才判"无归属"
- **被 `AGENTS.md` / `docs/` / `tests/` / `client/` / `server/` grep 命中路径或文件名** ← 这条最容易被跳过，代价最大：文档点名的工具可能只躺在 temp 一份（`drift_detector.py` 案例）。这类文件**先移出清理范围，另议归属迁移**，不要"顺手删了再改文档"
- 运行中终端的会话日志（先查终端状态，别按扩展名筛）

### 2. 跨项目性 → 移回，不再讨论可重建性

内容明显属于别的项目（其他仓库的状态文件、另一台机器的移交包）→ 归 Q3 移动，不能用"这个任务用完了"当删除理由。

### 3. 仓库注册对象 → 走对应协议，不能只删目录

`temp/` 里可以藏着**已注册的 git worktree**：`du` 排名很高（实测 63 MB / 732 个 `.py`），看起来像垃圾，实际是仓库注册对象。判定链：

```
.git 是 gitdir: 指针文件 → git worktree list 确认注册
  → 该 commit 是否 master 祖先（git merge-base --is-ancestor）
  → git status 是否 clean
  → 两者皆是 ⇒ 磁盘零独有内容，可回收
```

**顺序必须是：回收站删目录 → `git worktree prune`。** 只删目录不 prune 会留悬空记录；反过来图省事用 `git worktree remove --force` 是**永久删除**，违反硬约束 1。

### 4. 源码副本 → 先确认原始位置真的存在

"看起来像重复"不等于重复。738 个 `.py` 的副本按"`.py` = 临时脚本"的直觉筛选会被整份端掉。Q1 判"可重建"之前，必须实际验证原始 clone / 上游仓库在别处存在。
（实测案例：2026-10-22 `temp/_tarball_dl/` 的两个 tar.gz，`references/ZCode` 与 `references/deepseek-harness` 都在地 ⇒ 判可重建。**必须真的 `ls` 过那两个目录**，不能凭"references 应该有"推断。）

### 5. 系统运行时目录 → 单列，别当垃圾

`temp/` 里混着**后端代码定义、自建自清的运行时目录**，它们是系统的一部分，不是用户临时垃圾。判据：拿目录名去 `server/` / `client/` / `lib/` grep，命中 `Path` / `DIR` 常量即属此类。

| 目录 | 代码常量 | 行为 |
|---|---|---|
| `temp/terminals/` | `server/exec.py` `TERMINAL_DIR` | 终端输出真源；**运行中会话日志按活跃窗口保留** |
| `temp/exec_evidence/` | `server/exec.py` `EXEC_EVIDENCE_DIR` | 崩溃现场归档，**每类留最近 3 份后自动 prune**（ADR-0036 决策 5）；`mkdir(exist_ok=True)` 惰性重建 |
| `temp/write_backups/` | 写前备份 | 见 ADR-0036 |
| `temp/disk_scan_cache/` | `workspace/disk_manager/scripts/scan_disk.py` `CACHE_DIR` | 磁盘扫描缓存（`parents[3]/temp/disk_scan_cache`），**代码写死的路径**——清了脚本会重建，但别当垃圾定性 |

它们的**内容**可清（陈旧证据），但**定性必须写对**——2026-10-02 实测把 `exec_evidence/` 当一次性垃圾删了：行为无害（惰性重建），但归因错了，报给用户的结论就不成立。**任何 temp 清理都先跑一遍这个 grep，把系统运行时目录单列出来。**

### 6. 归属不明 / 跨项目 → ⛔ 先调查再问，不许直接问

**不许把"我没看过的东西"整批丢给用户问"删不删"**——用户不知道里面是什么，问了也只能瞎猜，等于把判定责任推回去。
2026-10-22 用户明确要求：「你看了再来问我决策，skill 里面写清楚」。

调查四步（缺一不可，做完才准开口问）：

1. **归属目录是否存在**：`ls` 过目标 workspace，**不能凭"应该有"推断**（见 §二.4）
2. **逐字节比对**：候选与归属目录的同名文件算 sha1，分成三类——纯副本 / temp 独有 / 内容不同
3. **读内容定性**：截图 vs 脚本 vs 日志。**截图与快照类不可重建**，脚本与日志通常可重建
4. **查是否已兑现**：patch 是否已应用、commit 是否已落地（见 Step 3.5；`git log --all --format=%s` 批量比对 subject）

⚠ **比对第 2 步前必须先分层：原图 vs 派生图（缩略图/转码/裁剪）**——不分层就会把派生图误判成"无源 = 不可重建"。
2026-10-23 实测：`temp/html/` 830 张 jpg 按文件名对 `<data_drive>:/<phone_sync_root>` 只有 142 张命中（17%），
一度被判成"大部分无源"。真因是混着两块：

- `media_form_groups/` 142 张 = **原图副本**（中位 1.48 MB）⇒ 同名同尺寸命中率 **100%**，纯副本
- `pose_picker/thumbs/` 688 张 = **生成的缩略图**（中位 8.8 KB，文件名 12 位纯 hex）
  ⇒ 按文件名在源里当然找不到，**但 `manifest.json` 逐条记着源路径**（688 条）⇒ 仍可重建

**派生图的可重建性看「生成它的清单/manifest」，不看源文件名。** 分层线索：尺寸量级（原图 MB 级 / 缩略图 KB 级）、
文件名是否程序生成的定长 hex、同目录有无 manifest / index.html 配套。

**报告格式：给拆分结论，不给整批是非。** 模板：

```
31 项里：
  11 张 png  = 云版界面截图，不可重建 ⇒ ★ 保护 / 移回 workspace/maa-patch/
  18 个 py   = 一次性探针 ⇒ ✅ 可删
  maa_commit/ = patch 已应用（证据：docs/environment-constraints.md 含"端口保留区"章节
                + git log 2 条命中）⇒ ✅ 可删
```

反例（❌ 不许这样问）：「maa 这 31 项要删吗？」

## 三、保护清单（按性质，不按名字）

| 性质 | 例子（**示例，非枚举**） |
|---|---|
| 个人创作与记录 | 笔记、日记、复盘、人生设计蓝图、财务账单、收藏导出数据 |
| 项目真源与工作记忆 | `temp/sdd/<slug>/`、`temp/planning_archive/`、`temp/handoff/`、`temp/wb_takeover/`、wip 关联物 |
| 唯一副本的源码 / 数据 | 未提交的产出、外部 clone、快照压缩包、注册表快照（系统状态已变就不可重建） |
| 仍在使用的校准基线 | OCR bbox 三档回归基线（升级 PaddleOCR/PaddleX 时要跑） |
| 系统运行时目录 | `temp/terminals/`、`temp/exec_evidence/`、`temp/write_backups/`——见 §二.5 |

**SDD 与 planning 归档是绝对保护**：`temp/sdd/<slug>/` 是上下文压缩后的恢复锚点（见 AGENTS.md「上下文压缩防护」），`temp/planning_archive/` 是只读历史归档。agent 不得擅自清理或移动；要归档由用户决策。

**`temp/handoff/` 也一律跳过**：它是换会话时的恢复锚点（`dev.handoff` 产出）。正常删除由写入侧做（写新稿时删旧稿、任务完成整份删），清理流程不参与，否则会把"正要接手"的稿清掉。**唯一例外是死稿**：状态为 `待接手` 且 mtime > 7 天，或状态为 `已接手` 且 mtime > 7 天、期间既无新稿也未完成——这类列进待定清单交用户裁决，不自动删。

**`temp/wb_takeover/` 同样跳过**：限流换号时 `wb-takeover` 出的接手包（HANDOFF + 全量对话 + 源 jsonl 拷贝 + 派发提示词），是"新会话要读的那份材料"。源 jsonl 在会话被删后就不可重建 ⇒ 一律保护；接手完成、对方确认能开做之后由写入侧删。⚠ 它与 `temp/handoff/` 的区别：那边是人写的交接稿，这边是机器生成的事实包 + 原文，覆盖重生成即可，所以只有整包删除、没有逐份改写。

`temp/` 正当用途本身不算垃圾：临时解压、临时查看、probe 现场，任务还在进行就保留。

## 四、工作流

### Step 1：扫描与判定

**同时按体积和条目数两个维度扫描**，别只排体积：

1. 列出 `temp/` 顶层（含大小、文件数、mtime）
2. **分桶统计**：`≥100 MB` / `10–100 MB` / `1–10 MB` / `<1 MB` 各多少项、各占多少体积和多少条目数。这张表直接暴露长尾（通常 <1 MB 那桶占 90%+ 条目）
3. 大块走三问（逐项读内容）；**长尾走第六节的批次判定，不许跳过**
4. 跑第二节五条交叉校验
5. 每一项落到：可删 / ★保护 / 📦移动 / ❓待定

### Step 2：生成清单并询问用户

**强制：删除/移动前必须给用户完整清单并获得明确同意。**

清单必须是**扫描时刻展开的具体路径快照**（落成文件，如 `temp/20261022_cleanup_list.txt`），**不能是删除时才求值的模式**——"根目录所有 `*.py`"这类活规则会连带删掉并发会话刚生成的文件。

清单**分两段**，两段都要有，不许只给大块段：

```
## 🗑️ 删除清单（送回收站，可恢复）
### A. 大块（按体积）
| 项 | 大小 | 判定依据（三问 + 校验） | 证据（含内容证据） |
### B. 长尾批次（按条目数）
| 批次 | 条目数 | 合计大小 | 批次抽样结论 | 依据 |

## 📦 移动清单（源 → 目标 / 大小 / 归属依据）
## ★ 保护清单（列出来让用户确认你没打算删）
## ❓ 待定项（说明分歧点）
```

每一项**必须附判定依据和证据**；删除项的证据栏必须含**内容证据**（一句话说明文件实际写的是什么，证明它被读过）。只有名字、大小、扩展名的行等于没读过，不得出现在清单里。

**清单用 Python 写文件生成，⛔ 别用 shell `printf` / `echo`**：Windows 路径里的 `\t`（如 `\temp\torch`）会被 shell 当成制表符并吞掉后续字母，2026-10-22 实测产出过 `...\localAgent\emp\orch-...whl` 这种坏行。

用 `AskUserQuestion` 批量问：① 大块段是否同意 ② 长尾批次怎么处理 ③ 待定项 ④ 是否发现遗漏任务需要建 wip。

> ⚠ 用户说"全部删"也不能覆盖保护类。清单里同时有垃圾和个人数据时，"全部删"字面执行会造成不可逆损失——把冲突**明确指出来**让用户确认，而不是照字面办。

### Step 3：执行前二次 diff

执行前重新扫一遍 temp，把**清单生成后新增的路径**剔除或补进清单。两道防线叠加：静态快照防"活规则端掉新文件"，二次 diff 防"漏掉新垃圾"。

### Step 3.5：按用户勾选批量执行前，必须再过四道校验（2026-10-03 新增）

用户勾选的是**簇级行**（一行可能覆盖十几个文件），而簇级描述是你自己写的 ——
**你写错的性质，用户勾了也不会纠正**。实测 182 项里因此救回 4 项，**全都是"多留"而非"多删"**：

| 校验 | 做法 | 实测救回什么 |
|---|---|---|
| ① 勾选行解析 | 正则取反引号 token；**range 写法要展开**；非文件名 token 靠磁盘存在性自然过滤 | — |
| ② 磁盘存在性 | 只删真实存在的；已不存在的说明上一轮已处理，别报失败 | 12 项 |
| ③ 活跃窗口 | `mtime` 在 2h 内的单独挑出 —— **多会话并发时可能是别的会话刚写的** | `h.txt`（01:43 另一会话产物） |
| ④ 引用扫描 | 仓库内找有没有文件提到这些名字 | `mem_watch.py`（`auto_shutdown` skill **活引用**它）、`handle.exe`、`read_office_text.py` |

**④ 的两个必须**：

- **一次遍历全树、批量匹配**所有候选名（读每个文件一次，`for t in targets: if t in txt`）。
  ⛔ **千万别按文件名逐个 `rglob`** —— 150 个候选 × 34786 个文件 ⇒ 2 分钟超时被后台化（实测踩过）。
- **子串命中必须做精确匹配复核**：判据是命中位置**前一个字符**不能是 `[A-Za-z0-9._\-/]`（实测 15 项命中里 4 项误报）。

**修正方向永远是"多留"**：把该留的**迁移到对应组件**（工具进 `tools/` 或组件 `tools/probes`、通用脚本进组件 `tools/` 并**按该目录命名约定改名 + 在 README 登记**，否则等于没迁），然后**同步改引用它的 skill 文档路径**，别留下死引用。

> ③ 命中时的处理：活跃窗口是**启发式不是死规则**。若该文件的使命已确定完成（有日志证明、源在别处、且只进回收站），可以放行，但**必须在报告里显式说明放行理由**。
> 实测：2026-10-22 的 3.98 GB torch wheel mtime 在 48 分钟前，靠三条证据放行——尺寸两次取样一致、`Installed 1 package` 日志、`.venv` 里 torch 可 import、uv 缓存源仍在。

### Step 4：删除（走回收站）

**唯一入口 `tools/disk/recycle.py`**（纯 ctypes `SHFileOperationW` + `FOF_ALLOWUNDO`）：

```bash
uv run python tools/disk/recycle.py --list <路径快照文件> --on-error continue
```

- 路径写**反斜杠绝对路径**；删除前逐行 `os.path.exists` 校验
- 有并发写入的场景用 `--on-error continue`（默认 `abort` 会因单个被占用文件中断整批）
- ⚠ **不要**改用 PowerShell `Add-Type ... Microsoft.VisualBasic`——本机 `Add-Type` 被安全策略拦截，照做必失败
- **禁用**：`Remove-Item` / `del` / `rm` / `rd /s /q` / `shutil.rmtree` / `git worktree remove --force`
- **校验真进回收站**：`recycle_audit.py` 全量扫描可能很慢（实测 5 分钟无输出）。要快就用 Python 解析 `$I` 元数据文件（`$Recycle.Bin\<SID>\$I*`，第 8 字节起 8 字节 = 文件大小，第 28 字节起 UTF-16LE = 原路径），按 mtime 过滤最近批次反查。⛔ 别用 PowerShell 比对中文路径（PS5.1 按 ANSI 读无 BOM 脚本 ⇒ 假阴性）

### Step 5：执行移动

`Move-Item` 即可（移动不涉及可逆性）。目标目录不存在先建；目标已存在同名目录时先确认内容再决定合并策略。业务数据从 temp 移到 `workspace/<task>/` 后，检查该任务是否需要 `manifest.toml`（见 cross_workspace_advisor / project_rules）。

### Step 6：wip 待办处理

- **发现遗漏任务**（中间产物对应的任务其实没完成）→ `wip_create`，`next_steps` 必须可执行
- **业务数据搬迁需要后续处理** → 建 wip 说明背景和下一步
- **发现归属错位的工具**（文档点名却躺在 temp）→ 单独提议迁到 `tools/` 并同步改引用，**不要混在删除动作里**

### Step 7：收尾报告（三指标，别只报空间）

1. **体积**：before → after（如 6.92 GB → 1.49 GB，−78%）
2. **条目数**：before → after（如 750 → 708），并说明**差值为什么不是删除项数**——并发会话期间新写入了多少（实测删 51 项但只净减 42 项，因为别的会话又写了 9 项）
3. **混乱度**：剩余项里还有多少说不出归属
4. 删除项数与 0 失败与否；移动项数与目标位置；新增 wip 待办
5. **主动交代操作期间的异常文件变动**——别的进程/会话写入或删除的东西要如实说明，别糊过去
6. 剩余 Top-N 大块（让用户知道体积还剩在哪）

## 五、规则

### 硬约束（不可违反）

1. **删除必走回收站**：只用 `tools/disk/recycle.py`；禁用 `Remove-Item`/`rm`/`shutil.rmtree`/`git worktree remove --force`
2. **清单先行 + 明确同意**：任何删除/移动前必须给完整清单并获用户同意；用户说"全部删"不覆盖保护类，冲突必须指出
3. **清单是静态路径快照**：扫描时刻展开成具体路径文件，禁止"所有 `*.py`"这类执行时求值的活规则；执行前二次 diff 新增项；**用 Python 生成，不经 shell**
4. **判"可删"前必须读过内容**：每个拟删文件实际读 ≥30 行（大文件头 30 + 尾 30，不足 30 行读全文），清单证据栏必须有内容证据；**禁止仅凭文件名/扩展名/目录名/体积下结论**，"可重建"还须验证重放路径现在真能跑通（见第一节前置）
5. **活跃文件不删**：2 小时内的 mtime / wip 关联 / 被 `AGENTS.md`·`docs/`·`tests/`·`client/`·`server/` grep 命中 → 一律移出清理范围（放行须显式说明理由，见 Step 3.5）
6. **保护类不删**：个人创作与记录、项目真源（SDD / planning 归档）、唯一副本、在用校准基线。**唯一豁免**：`temp/handoff/` 下的死稿（`待接手` 且 mtime > 7 天；或状态为 `已接手` 但 mtime > 7 天、期间既无新稿也未完成），经用户逐项确认后可送回收站——它是恢复锚点，正常路径由写入侧自己删，只有确认"不会再有用"才清
7. **业务数据只移不删**
8. **永久删是条件句**：默认只送回收站；**仅当用户明确要腾空间**才 `recycle_audit.py` 确认入站 → `recycle_purge.py --entry ID=原路径 --yes`。⛔ 不许把"清理"默认理解成"要释放空间"
9. **三个指标一起压**：体积、条目数、混乱度。⛔ 不许只按体积排 Top-N 就把长尾略过——条目数的大头就是小文件
10. **验收看归属**：清理后每一项都要能说出归属，说不出 ⇒ 归位或进删除清单，不许原地"待定"

### 经验做法（可调整）

- 先按顶层目录分类再下钻；性质从读过的内容得出，别从目录名/文件名推断。抽样只用于**快速排除**整个目录/批次，不能用来给单个文件定罪
- ⛔ **别用文件名正则自动归类就直接删**（2026-10-02 实测）：用正则把 571 个根散文件分桶时，**子串匹配**会误判——`kana_probe.py` 因含子串 `a_probe` 被归进"讲稿产物"。**分类只是候选，进删除清单前必须用内容证据逐组复核**
- 清单做**反向校验**：确认近期活跃文件没被误纳入
- 判"一次性脚本的任务是否已完成"：取脚本名里的批次/任务标识去查 wip 或对应 ledger 是否已提交，比内容比对可行得多
- 收尾把分类决策和发现写进记忆（`.agents/memory/YYYY-MM-DD.md`），方便下次清理
- 与 `tools/` 重复的脚本可以直接删，但**内容比对是可选优化项，不是删除前置条件**——一次性脚本与通用工具几乎永远不会字节相同。⚠️ 这里豁免的只是**逐字节比对**，不豁免硬约束 4 的**读内容**

## 六、长尾散项：必须成批处理，不许因为"体积小"跳过

### 为什么必须走批次

硬约束 4 要求"每个拟删文件读 ≥30 行"。面对 600+ 个散文件，逐个读不可执行 ⇒ 结果是长尾永远没人碰，
**条目数永远压不下来**（这正是 2026-10-22 删了 4.97 GB 却只净减 42 个条目的原因）。

### 解法：把判定单位从「文件」换成「批次」

**同批次可以共享证据，但必须满足下面三条，否则退回逐文件判定。**

1. **批次怎么划**：按「同一次任务留下的痕迹」划分，证据是**前缀 / 日期戳 / 目录名**三者之一：
   `20261021_*`（同一天一批探针）、`pytest_*`（同一类 basetemp）、`hw_exp2_*`（同一作业）。
   ⛔ **别按扩展名划批**——`.py` 里混着一次性脚本和通用工具，`.json` 里混着 dump 和配置。
2. **批次内抽样真读**：每批抽 3–5 个代表（覆盖最大 / 最小 / 不同扩展名），逐个真读 ≥30 行。
   抽样结果**全同性质** ⇒ 整批按该性质判定；
   **出现任何一个"唯一副本 / 被引用 / 不可复现"信号** ⇒ 停止批量判定，逐文件过。
3. **批次级校验**：活跃窗口按批次内**最新 mtime** 算；引用扫描按批次名**一次遍历全树批量匹配**（见 Step 3.5 ④）。

### 长尾的四档处置

| 档 | 判据 | 处理 |
|---|---|---|
| 同批次一次性产物 | 抽样全是同一次任务的中间 dump / 探针输出 | ✅ 整批删 |
| 有归属但错位 | 属于某个 workspace / 组件 | 📦 整批移回归属地（**并登记**，否则等于没移） |
| 跨批次杂烩 | 抽样性质不一致 | 拆批重划；拆不动就逐文件过 |
| 说不出归属 | 抽样读不出来历 | ❓ 交用户，**不许默认留在原地** |

### 长尾清理的收益要写清楚

清 670 个散文件只回收 24.5 MB——**这一档的价值是条目数和混乱度，不是空间**。
在清单和报告里照实说，别用"只回收 24 MB"暗示它不值得做，也别用"清了 670 项"虚报空间收益。

## 七、常见发散（本 skill 被误读过的地方，动手前扫一眼）

| 误读 | 实际 |
|---|---|
| "清理 = 腾空间" ⇒ 顺手补一个永久删步骤 | 用户说"清理/整理"是要**去乱**。**只有点名要空间才 purge**（见 §零 与硬约束 8）。2026-10-22 因此被纠正一次 |
| "按体积排 Top-N 就够了" | 体积与条目数不相关。只按体积清，条目数几乎不动（实测 −6%） |
| "小文件不值得处理" | 条目数的大头就是小文件（实测 94.5% 条目 <1 MB）。条目数是独立指标（硬约束 9） |
| "每个文件都得读 30 行，做不完就不做" | 长尾走**批次判定**（第六节），既不退回逐文件，也不许跳过 |
| "给 temp 建个规整目录结构" | 见第八节：temp 是堆积区，不强加结构 |
| "条目数压不下来 = 我没清干净" | 也可能是**并发会话在持续写入**。2026-10-22 一轮清理期间，别的会话新写了 50+ 个 `agent_browser_*` 文件。收尾必须如实区分「我删了多少」与「期间新增了多少」，别把新增算成没清干净 |
| "清单生成完就照着删" | 清单生成后要**自检一次**：删除组里有没有混入自己在保护清单里声明过的前缀（实测把 9 个 `hw_*` 作业线文件写进了删除组，自相矛盾）。修正方向永远是**多留** |

## 八、关于目录结构

**temp 无固定结构，不要强加。** 它是临时堆积区，不是有治理结构的项目目录。历史上本 skill 曾规定"清理后应该有 `refs/`、`scripts/`、`html/` 等"，结果是 agent 花力气把文件塞进"应该有的"目录（无意义劳动），或结构图与实际脱节沦为废文档。

清理的目标是**压体积、压条目数、压混乱度**，不是**整形**。
