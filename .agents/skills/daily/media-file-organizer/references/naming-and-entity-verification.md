# 命名、日期取证与官方名核对

## 1. 命名格式

```
M-D 角色 版本.ext
```

| 项 | 规则 | 例子 |
|---|---|---|
| 月 / 日 | 不补零 | `8-3`、`10-11` |
| 分隔 | 单个半角空格 | `8-3 提丰 原画.mp4` |
| 角色 | 保留文件原写法，最后一步再核官方名 | `蕾米` → 收尾核为 `蕾米埃尔` |
| 版本 | 独立视频默认 `原画`；差分包产物默认 `差分`；同日同角色多份 → `差分1` / `差分2` | `8-3 提丰 差分1.mp4` |
| 非法字符 | `\ / : * ? " < > |` 一律不出现 | — |

**为什么要「先保留原写法」**：这批素材跨多个游戏/IP，文件夹名里的角色名常常是音译、简称或
同人叫法。过早按"规范名"批量替换会丢线索，而且一旦替换错，原写法就找不回来了。
正确顺序是：先按原写法落定 → 全部完成 → 每个可疑名单独查证 → 只改有证据的。

## 2. 日期取证（优先级从高到低）

1. **用户明确给的清单**（最高权威）。
2. **zip 内部 entry 名**。实测：
   - `祀8-21.zip` 内是 `小葱8-21.exe` ⇒ 日期 8-21、角色 小葱；
   - `9-7蕾米埃尔.zip` 内是 `9-7蕾米差分.exe` ⇒ 版本是「差分」。
   zip 名与内容不一致是常态，**只信 entry**。
3. **MP4 `mvhd` 的 creation_time**。
4. **所在子目录名**（如 `10-11\洛茜原画.mp4`）。
5. **mtime**：❌ 不可用。整批 142 个文件的 mtime 全是同一天（复制/解压时间），
   与原始发布日期无关。

### 2.1 `mvhd` 解析要点

MP4 是 box 结构。`ftyp` 之后逐个 box 顺序读头（`size` 4B + `type` 4B；`size==1` 时后跟
8 字节 largesize；`size==0` 表示到文件末尾），遇到 `moov` 就把它读进内存再找 `mvhd`
（`moov` 很小，给 16 MB 上限足够）。

`mvhd` 载荷：

| 版本 | 布局 |
|---|---|
| v0 | `version(1)+flags(3)` + `creation(4)` + `modification(4)` + `timescale(4)` + `duration(4)` |
| v1 | `version(1)+flags(3)` + `creation(8)` + `modification(8)` + `timescale(4)` + `duration(8)` |

- `creation` 是 **1904-01-01 UTC 起的秒数**，换算：`datetime(1904,1,1) + timedelta(seconds=creation)`；
- 时长 = `duration / timescale`，用来确认「它真是个能播的视频」（本次样本 9.7–17.2 s）。

⚠ 实现坑：如果用一个递归函数找 `mvhd`，**必须把内层返回值一路 `return` 上来**。
本次第一版忘了回传，所有文件都解析出 `None`，一度误判「这些 mp4 全是坏文件」。

## 3. zip 取证

```python
with zipfile.ZipFile(path) as z:
    for info in z.infolist():
        encrypted = bool(info.flag_bits & 0x1)
        print(info.filename, info.file_size, encrypted)
```

实测会遇到的形态：

- entry 是 `.exe`（差分包的播放器封装）；
- entry **没有扩展名**；
- 一个 zip 装 **2 个视频**；
- entry 带嵌套路径（`xxx/yyy.mp4`）；
- 包里有 `.txt` 说明文件（解压时用 `-x!*.txt` 排除）；
- 加密包（ZipCrypto），密码由用户提供。

**排除巨型无关包**：目录里若混入软件/引擎安装包（本次是 `Goo-Engine`，内部 5995 条），
扫描时会把清单撑爆、上下文打满。扫描器必须先按文件名排除，或给 entry 数设上限并打印
`matched/N`，让「抽不到」暴露出来而不是伪装成「没有」。

## 4. 加密 zip 解压

```
7z.exe x <zip> -p<password> -y -o<staging> -x!*.txt -bb0 -bso0 -bsp0
```

- 用 7-Zip 而不用 Python：纯 Python ZipCrypto 约 **1.8 MB/s**，7z 快 10–50 倍；
- **每个 zip 一个独立 staging 目录**，不要共用一个输出目录（同名会互相覆盖）；
- 解完先校验（大小 > 0、MP4 头 `ftyp`），再搬到目标名；
- 脚本要幂等：目标已存在且大小/头正确 → 跳过。中断后可原样重跑。

### 4.1 双层 7z：外层不加密、内层加密（扩展名还写错了）

2026-10-24 在 `<data_drive>:/<bilibili_videos>作品` 实测的形态：

```
xxx.7z（外层，普通 7z，1 个条目）
└─ xxx.z7（内层，文件名少一个 7，但文件头 377abcaf271c = 标准 7z）
   └─ xxx.mp4
```

- 内层 next-header 首字节 `0x17`（EncodedHeader）⇒ **文件头加密**，不输密码连条目都列不出来；
- 空密码/旧密码的报错是 `Cannot open encrypted archive. Wrong password?`，不是"文件损坏"；
- **不要用少量样本外推**：这批 445 个包里 443 个双层、**2 个是单层直出 mp4**
  （`奥黛丽1.7z`、`初音应援.7z`）。抽 10 个全双层就写死双层分支，跑到第 46 个才炸。
  正确做法：先对全部外层跑一次 `7z l -slt`（只读表头、很快）建清单，按条目类型分派；
- 执行器必须同时支持「条目是媒体 → 直接用」和「条目是压缩包 → 解密再解」两条分支；
- 幂等检查按目标名：`<包名>.mp4` 已存在且头有效就跳过，这样中断后重跑能自动续上；
- 密码只经环境变量传入，不写进脚本、不写日志、不打印。

## 5. 官方名核对

### 5.1 流程

1. 从最终清单里挑可疑名：音译（`卡夫卡`）、简称（`蕾米`、`卡提`）、明显异体（`佩里卡`、`清霄`）；
2. 逐个 `WebSearch`，优先游戏 wiki / 官方公告 / 官方立绘页；
3. 找到「同一角色 + 同一作品」的明确对应才改名；
4. 拿不准 → **保留原写法**，在交付说明里单列「待确认」。

### 5.2 跨 IP 同名陷阱（本次最重要的一条）

| 名字 | 归属 | 结论 |
|---|---|---|
| 提丰 | 明日方舟 | —— |
| 提弗洛斯 | 终末地「再旅者」 | **不同角色，不合并** |

同一批素材来自多个游戏时，「看起来像同一个人的两个名字」必须分别查两个作品的 wiki。
把两个 IP 的角色合成一个名字，比保留一个"不够规范"的原名严重得多。

### 5.3 本次实际修正（15 条，作为对照样例）

| 原写法 | 官方名 | 依据 |
|---|---|---|
| 卡夫卡 | 卡芙卡 | 崩坏：星穹铁道 |
| 佩里卡 | 佩丽卡 | 明日方舟：终末地 |
| 清霄 | 清宵 | 对应作品 wiki |
| 达尼娅 | 达妮娅 | 对应作品 wiki |
| 蕾米 | 蕾米埃尔 | zip 内名为 `9-7蕾米差分.exe`，与角色名互证 |
| 卡提 / 卡提西亚 | 卡提希娅 | 对应作品 wiki |

规律：**同音不同字**是主要错误类型（夫/芙、里/丽、霄/宵、娅/妮）。核对时关注读音相同、
字形不同的候选，而不是找"完全不同的名字"。

## 6. 冲突消歧

同一角色同一天有多个版本时：

```
8-3 提丰 差分1.mp4
8-3 提丰 差分2.mp4
```

不要用 `(1)`、`_v2`、`副本` 这类后缀——它们不在命名规范里，且排序结果不稳定。
