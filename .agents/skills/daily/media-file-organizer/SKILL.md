# 媒体文件夹整理与重命名

> ⚠ **本 skill 的第一原则来自一次真实事故**：用户上一个「执着于脚本一键完成」的流程
> **误删了他全部文件**。所以这里的批处理不是「多加几个校验的一键脚本」，而是
> **映射表先行 + 分批执行 + 每批回读**。任何让你「顺手把整个目录一次处理掉」的冲动都必须压住。

## 适用 / 不适用

| 适用 | 不适用 |
|---|---|
| 一个乱文件夹里混着视频、图片、加密 zip、子目录、临时文件 | 单一明确文件的改名/移动（直接做，不用走流程） |
| 需要「平铺 + 统一命名 + 剔除杂物」 | 需要按内容语义分类归档（走 `file_classifier` 一类工具） |
| 差分/版本包要解压成独立文件 | 单纯删文件（走 `windows-recycle-and-space-reclaim`） |

### 两种模式

| 模式 | 场景 | 走法 |
|---|---|---|
| **全量整理** | 一个新的、混装的目录 | 本文第 0–6 步 |
| **增量入库** | 固定库 + 新批次（用户说「更新了，分别放进去」） | [`references/bilibili-works-ingest.md`](references/bilibili-works-ingest.md)：`plan` → 人工复核 → `run` → 验收/回收 |

固定库目前有两个，**互相独立、命名不同、绝不能混放**：
`<data_drive>:/<bilibili_videos>作品`（`角色X.Y.mp4` + 月份子目录，来源是平铺 7z）与
`<data_drive>:/<media_staging>\new`（`M-D 角色 版本.mp4` + 平铺，来源是按日期分的 zip）。
判库看命名形态，不看角色名——两边都会有同角色。

增量入库不是把全量整理再跑一遍：它只处理新批次，目标目录已存在，**预检与回读的判据是「原数量 + 本次数量」**。

## 用户偏好（默认值，不必再问）

| 偏好 | 依据 |
|---|---|
| **分批做，宁可一个一个来** | 原话：「建议是你找一些格式相近的一批一批做，大不了一个一个做」 |
| **不依赖一键脚本** | 原话：「上一个执着于脚本一键完成的误删了我的所有文件」 |
| 删除只送回收站 | 项目规则；用户要可回滚 |
| 角色名**先保留原写法** | 素材跨多个游戏/IP，「规范名」常是错的；收尾再查 |
| 拿不准就问一次，其余按默认 | 「按默认处理」；默认值写成本节的推荐项 |
| 视频**平铺在一个文件夹** | 原话「就把全部视频摊开」 |
| 清单/报告放**父目录** | 平铺目录只留媒体文件 |

## 第 0 步：确认四件事（一次 AskUserQuestion 问完，别逐条打断）

在动任何文件之前问清楚：

1. **zip 怎么处理**：解压平铺（推荐）/ 原样保留 / 整包移走
2. **mp4 怎么处理**：原地改名（推荐）/ 复制到新目录（保原件）
3. **杂物（txt / exe / 截图 / 空子目录）**：全部送回收站 / 只挪视频、保留其它
4. **名字口径**：先保留文件原写法、收尾统一核对官方名（推荐）/ 一开始就按官方名

第 4 条的推荐值不是客套：**跨游戏/IP 的「规范名」经常是错的**，先改动会丢掉原始线索。
用户明确表达过「先保留原写法，收尾查一轮再决定」——这是默认行为，不必再问一遍。

**若用户没有明确删除授权 → 只做改名/解压，不动杂物。**

## 第 1 步：只读盘点，产出映射表（不写一个字节）

```bash
cd /f/<project_root>
./.venv/Scripts/python.exe .agents/skills/daily/media-file-organizer/scripts/scan_media.py "<data_drive>:/<media_staging>\new" \
    --out temp/media_inventory.csv
```

脚本只读，输出：文件名、大小、类型、mtime、**MP4 `mvhd` 拍摄时间**、**zip 条目清单/是否加密**、
首 4 MB 指纹（用于查重）。

拿到清单后，写一个**一次性 mapping 脚本**到项目 `temp/`（**不是**目标文件夹里），产出 CSV：

```
kind,source,zip_inner,size,target,date,character,version,action,note
```

### 盘点必须做三条覆盖检查（缺一条就会漏文件）

1. **覆盖**：目录内每个文件（含子目录内）在映射表里**恰好出现一次**；
2. **唯一**：`target` 集合无重复（Windows 大小写不敏感，按 `casefold` 比）；
3. **不冲突**：任何 `target` 不等于已存在的文件名，也不等于同批里另一个 `source`。

> 实测坑：第一次盘点漏了子目录里的 `10-11\洛茜原画.mp4`，靠第 1 条检查才发现。
> 这类漏项不会报错，只会「安静地少一个」。

**扫描前先排除巨型无关包**：目录里若有几百 MB 的软件安装包/引擎包（本次是 `Goo-Engine` zip，
内部 5995 个条目），先按文件名排除，否则清单会被它淹没。

## 第 2 步：定名规则（先在映射表里算，不要边改边想）

### 2.1 基本格式

```
M-D 角色 版本.ext        例：10-4 提丰 原画.mp4
```

- 月、日**不补零**（`8-3` 不是 `08-03`）；
- 默认 `原画` 给独立 mp4，`差分` 给差分包的产物；同日期同角色多份时用 `差分1` / `差分2`；
- 角色名与版本之间只有一个空格；文件名里不出现 `\ / : * ? " < > |`。

### 2.2 日期从哪来（优先级从高到低）

1. 用户给的清单 / 命名要求；
2. **zip 内部文件名**（`祀8-21.zip` 里装的是 `小葱8-21.exe` ⇒ 日期 8-21、角色 小葱）；
3. **MP4 `mvhd` 的 creation_time**（脚本已解析，1904 纪元，需减 2082844800 秒）；
4. 所在子目录名（`10-11\...`）；
5. ❌ **mtime 不可信**：这批 142 个文件的 mtime 全是同一天，是**复制时间**不是发布日期。

### 2.3 内容从哪来

- zip：看 **entry 名**，不要看 zip 名。实测有 zip 名与内容完全不同、一个 zip 装 2 个视频、
  entry 是 `.exe` 甚至**无扩展名**、entry 带嵌套路径等情况；
- 视频：`mvhd` 能确认它是有效视频（时长 9–17 s 量级），也能补出丢失的日期。

细节（含 `mvhd` 结构、7z 参数、官方名核对方法）见
[`references/naming-and-entity-verification.md`](references/naming-and-entity-verification.md)。

## 第 3 步：分批执行（本次的核心纪律）

### 3.1 怎么分批

按**同格式 + 同月份**切：`mp4 M1..M5`、`zip Z1..Z5`，每批 10–30 条。
短视频改名一批、加密 zip 解压一批、某个大月份单独一批——**批次之间互不依赖**。

### 3.2 每一批的动作顺序

```
预检（全部条目） → 逐条执行 → 回读（数量/大小/名字） → 报告 → 下一批
```

**预检**每条都要过：源存在、目标不存在、源大小 > 0、类型与映射表一致。
**任何一条预检失败就整批停**，报告是哪条、为什么，不要「跳过它继续跑」。

**逐条执行**：

| 动作 | 正确写法 | 为什么 |
|---|---|---|
| 改名 | `os.rename(src, dst)`，先断言 `not os.path.exists(dst)` | 不要用会静默覆盖的写法；本机 `os.replace` 会直接盖掉 |
| 解压 | 每个 zip 一条 `7z x`，解到独立 staging 目录 | 不批量塞进一个目录，避免同名互相覆盖 |
| 搬运 | 解出的 mp4 先落 `.extract_part`，校验后再 `os.rename` 到目标 | 中断时目标目录里不留半截文件 |

**回读**：`len(os.listdir(dir))`、目标条数、总字节数，与映射表算出来的期望值**逐项相等**。
回读不是「看一眼没报错」，是要有数字对比。

### 3.3 两个必须处理的边界

- **改名成环**：若 `A→B` 而 `B` 也是本批的 source，直接 rename 会互相踩。先把整个环改成
  临时名（`__tmp_<i>`），再改成终名；
- **staging 目录名**：源名和 zip 内路径里常带 `\` `/`。拼临时路径前必须替换掉，
  否则会**在 staging 下造出意料之外的子目录**（本次踩过）：

  ```python
  safe = (source + "__" + zip_inner).replace("\\", "_").replace("/", "_")
  ```

### 3.4 加密 zip 用 7-Zip，不要用 Python `zipfile`

本机实测：Python 的 ZipCrypto 解密是纯 Python 实现，约 **1.8 MB/s**，79 个包要跑一小时以上；
7-Zip 快 10–50 倍。单包耗时实测：17 个视频 56 s、25 个视频 59 s、13 个视频 15–18 s。

```python
args = [SEVENZIP, "x", src, f"-p{PASSWORD}", "-y", f"-o{tmpdir}",
        "-x!*.txt", "-bb0", "-bso0", "-bsp0"]
```

- `-bso0 -bsp0` 抑制刷屏输出；`-x!*.txt` 排除包内说明文件；
- 解压脚本要**幂等**：目标已存在且大小/头正确就跳过——这样中断后重跑不会重复劳动；
- 密码从用户处获取，**不要写进脚本/日志**。

## 第 4 步：杂物与旧包送回收站（禁止物理删除）

1. **先出回收清单**（路径 + 大小 + 归属批次），给用户看；
2. **探针**：先用 `tools/disk/recycle.py` 删一个无价值文件，确认工具可用；
3. **分组执行**：按子目录/根文件分组，一组一组删，每组后回读剩余；
4. 校验：剩余文件集合 == 映射表里「应保留」的集合；
5. staging / `.extract_part` 这类自己造的临时目录也要走回收站，不要 `rmtree`。

```bash
./.venv/Scripts/python.exe tools/disk/recycle.py "<绝对路径>"
```

本机所有 `rm` / `del` / `Remove-Item` / `shutil.rmtree` 都被 shim 转成「送回收站」，
但**不要依赖 shim**——脚本里直接调 `tools.disk.recycle.send_to_recycle`，理由与陷阱见
`windows-recycle-and-space-reclaim` skill。

## 关键规则（硬约束）

- **绝不**写「一条命令处理整个目录」的脚本；必须分批，批与批之间可中断、可复盘。
- **绝不**用 `rm` / `del` / `shutil.rmtree` / 覆盖式移动删除任何用户文件；只走回收站工具。
- **绝不**覆盖已存在的目标文件。目标存在 = 立刻停下报告。
- **绝不**凭 zip 名 / 文件名猜内容；看 entry、看 `mvhd`。
- **绝不**在盘点前动手改名；映射表是唯一执行依据。
- **绝不**在目标文件夹里创建脚本、临时目录、日志、CSV。
- 角色名**先保留原写法**，官方名核对作为独立最后一步，只改有证据的。
- 每批执行完**必须回读并对比数字**；没有数字就没有通过。

## 坑点清单（都是踩过的）

| 坑 | 现象 | 处置 |
|---|---|---|
| mtime 是复制时间 | 所有文件同一天 | 用 `mvhd` / zip 内名 / 目录名推日期 |
| 盘点漏子目录文件 | 不报错，少一条 | 覆盖检查：每个文件恰好一次 |
| staging 名含 `\` `/` | 解压目录里冒出意外子目录 | 拼路径前替换成 `_` |
| 巨型无关 zip 混入扫描 | 一次 dump 925 KB 条目，上下文被打爆 | 按名排除，或给 entry 数设上限 |
| Python 解密 zip 极慢 | 1.8 MB/s，误以为卡死 | 换 7-Zip；脚本做成幂等可续跑 |
| 7z 脚本参数校验写错 | `Z1` 与 `1..5` 直接比，永远不匹配 | 先剥前缀再比，且打印实际解析值 |
| 回收预检用了绝对路径比相对表 | 全部误判为「还有残留」 | `os.path.relpath(path, ROOT)` 后再比 |
| `mvhd` 递归没回传结果 | 解析返回 None，误判文件无效 | 递归返回值要一路 `return` 上来 |
| 同名目标 | 覆盖 = 数据永久丢失 | 预检 + `差分1/差分2` 消歧 |
| 跨 IP 同名合并 | 两个角色被写成同一个 | 分开查 wiki，确认不是同一角色 |
| 把清单写进平铺目录 | 交付目录不再干净 | 清单放父目录 |

## 输入 / 输出

- **输入**：一个待整理的本地目录（绝对路径）+ 用户的命名口径与删除授权
- **输出**：平铺目录（只含最终媒体文件）+ 父目录下四份 CSV 清单 + 一份核对报告
