# 案例：派单提示词「多版本 vs 单版本」到底谁定的

> 会话 `46e11254-ae4e-4cca-af04-1c2626944c51`（2026-10-28 13:31 起）。
> 条目号 = `uv run python -m tools.wb_history dump 46e11254` 输出里的 `[n]`。
> ⚠ **编号口径 = 2026-10-29 版脚本**。2026-10-30 加了 task-notification / 续写指令过滤后编号整体前移
> （同一条现在约在 `#120` 附近）。复现请用**关键词 + 时间**定位：`dump 46e11254 -k 只保留当前 -c 2`。
> 本案例的作用：证明「只读用户说了什么」会读出错误结论。

## 1. 起因

2026-10-29 用户问：「多版本管理怎么界面上没有了」。
只看用户侧（`--user-only`）时能捞到三条：

| 条目 | 时间 | 用户原话要点 |
|---|---|---|
| `[96]` | 10-28 17:43 | 「我们提供提示词版本管理和回滚吧……最多保存 10 个版本……用户可以查看、复制或删除某一个版本……**不允许修改历史版本**」 |
| `[121]` | 10-28 21:41 | 「这一版很多话都没有说清楚……」+「**不做多版本的保存，只保留当前这一个版本**」 |

光这两条 ⇒ 结论会是「用户 4 小时内自己改主意、还少了功能」。**方向对，证据不足**：中间发生了什么完全空白。

## 2. 补上 agent 侧之后

| 条目 | 角色 | 时间 | 首句 |
|---|---|---|---|
| `[96]` | U | 17:43 | 提多版本规则（10 版 / 不可改历史 / 可看可复制可删） |
| `[97]` | A | 17:47 | 「现在给存储层添加提示词版本方法」 |
| `[98]` | A | 17:51 | 「现在把状态和事件处理接到 `App.vue`」 |
| `[99]` | A | 18:00 | 「四条都处理了，其中一条和你记的位置不一样」 |
| `[120]` | A | 21:22 | 「改完了。你提的六条都已处理」+「清理多余的话：2666 → 2030 字符」+ 四个提示词变体矩阵 |
| `[121]` | U | 21:41 | 「**这一版**很多话都没有说清楚……不做多版本的保存」 |

关键收获三条：

1. **`[121]` 里的「这一版」指的是 `[120]` 21:22 交付的那一版**。脱离 agent 侧，这句指代什么完全无法还原——这是「只读用户侧」最典型的断链。
2. **多版本在 `[97]`–`[99]` 已经真的实现了**。用户是在看到实现之后才否掉的，不是「说了没做」。只看用户侧会得出「用户先要后不要」的自相矛盾，看不到中间那段施工。
3. **用户否掉多版本和「四种变体」是在同一段里说的**，`[120]` 里那两个矩阵就是被吐槽的对象。要把「版本保存」和「提示词变体」分开读，否则会把两件事捆在一起处理。

## 3. 结论（写文档时该记的）

- 现行口径 = **单版本**（`[121]` 21:41 裁定），推翻 `[96]` 17:43 的 10 版方案。
- 推翻记录要连**起因**一起留：`[97]`–`[99]` 已完成多版本实现，`[120]` 的变体矩阵是触发点。
- 用户 10-29 又说「界面上没法回滚和切换……别的版本应该可以删、可以看、可以改」⇒ 口径再次变化。**裁定会被后一批推翻，文档只留「现行口径 + 推翻链」**，别把任何一版当永恒真理。

## 4. 方法教训

- `dump` 默认出双方；要引「用户逐字原话」再 `--user-only`，**但判断语境时必须回来看 A 侧**。
- 看到用户一句「不是这样 / 这个不对 / 这一版」时，**先往上翻一条 A**，否则必然猜错指代。
- 引 agent 的话必须标 `A`，把 agent 的方案写成用户要求 = 伪造原话。
