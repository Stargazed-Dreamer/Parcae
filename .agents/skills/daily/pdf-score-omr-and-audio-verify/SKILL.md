# 乐谱 PDF → 机器可读 + 与音频交叉验证

## 0. 先花 5 秒排除 OMR

```python
import pymupdf; d = pymupdf.open(pdf)
print(d.embfile_count())          # >0 则直接取内嵌 MusicXML，别做 OMR
print(d.metadata)                 # creator 告诉你制谱软件（Sibelius / MuseScore / Finale）
```
Sibelius/Finale 导出的 PDF **不内嵌** MusicXML（实测 `embfile_count()==0`）⇒ 必须 OMR。
MuseScore 有时会内嵌，先查。

## 1. OMR 选 Audiveris，不要选 oemer

- ❌ **oemer 0.1.8（PyPI 最新）在现代栈上跑不了**：它的 checkpoint 含**负 pad 的 ConvTranspose**，
  onnxruntime ≥1.22 直接 `ShapeInferenceError: Attribute pads must not contain negative values`；
  降到 ORT 1.17.3 又要求 `numpy<2`，而新 scipy 要 `numpy>=2`（且老 scipy 用已删除的 `np.long`）⇒ **依赖地狱**。
  ⚠️ 更糟：装 oemer 会把 `onnxruntime` 换成 `onnxruntime-gpu`、把 `cv2` 从 4.x 顶到 5.x。
  **如果你有别的项目共用这个 venv，装之前先另开一个 venv。**
- ✅ **Audiveris**（Java，已到 5.11.x）：对干净的雕版谱质量明显更好，自带 JRE。
  需要 JDK/JRE ≥17（本机 JDK 21 可用）。

## 2. 拿 Audiveris（Windows，免安装）

官方只发 MSI。**不要双击安装**——`msiexec /a` 可**无需管理员**解包出真实文件名：

```bash
# GitHub release 直连常被挡，走镜像（gh-proxy.com / ghproxy.net 可用；ghfast.top / mirror.ghproxy.com 不通）
curl -sS -L --ssl-no-revoke -o audiveris.msi \
  "https://gh-proxy.com/https://github.com/Audiveris/audiveris/releases/download/5.11.0/Audiveris-5.11.0-windowsConsole-x86_64.msi"
# 取资产列表用 api.github.com（它可直连）
MSYS2_ARG_CONV_EXCL="*" msiexec /a "$(pwd -W)/audiveris.msi" /qn TARGETDIR="$(pwd -W)/audiveris"
# ⛔ 别用 7z 解 MSI —— 只得到 fileXXXX，文件名表丢了
```
选 **windowsConsole** 变体（控制台有输出）。解出 `Audiveris/Audiveris.exe` + `Audiveris/app/audiveris.jar` + `runtime/`。

## 3. 批量跑

```bash
Audiveris.exe -batch -export -output <outdir> -force <input.pdf>
```
- 支持多页 PDF，输出**一个** `<name>.mxl`（压缩 MusicXML）+ `.omr` 工程 + `.log`。
- 常见 `NullPointerException ... "event.timeOffset" is null`（Wedge/8va 处理缺陷）是 **WARN，不影响导出**。
- 对照 `-batch` 是否真跑完：看 log 里 `exported to ...mxl`。

## 4. 解析（music21）

```python
import music21 as m21
s = m21.converter.parse('x.mxl')
# ⛔ 大坑：note.offset 是**相对所在 Measure** 的！直接用会把上千个音压到几十个位置。
#   要绝对位置必须 flatten：
for p in s.parts:
    for n in p.flatten().notes:      # flatten 后 offset 才是绝对四分音符数
        print(n.offset, n.pitch.midi if n.isNote else [x.midi for x in n.pitches])
s.write('midi', 'x.mid')
```

## 5. 验证"这份谱 = 那条演奏"

不要只看时长/调号（弱证据）。两条硬判据：

1. **音级分布相关**（12 维）：谱面 note-heads 的 pitch-class 归一化直方图 vs 音频转谱的
   时间加权活动直方图。**r>0.99 才算强证据**；再看最稀有的两三个音级两边是否同样稀有
   （同调性但不同曲也会撞调号，稀有音级同时稀有才是指纹）。
2. **时间分辨**：把进度切成 20 段，逐段算上面的 12 维相关。判据：**大多数段正相关、中位 >0.85**。
   唯一负/低的那段通常是稀疏段或**变速处被线性进度映射拉偏**——不要因此否掉结论，但要在报告里说明。

音频侧从音频转谱模型（如 piano_crnn.onnx）拿钢琴卷；注意 onset 阈值去重（同一延音会反复越阈）。

## 6. 报告里必须写清的诚实边界

- **OMR 有误差**（Audiveris 也会漏/多识别），所以 **PDF 原件才是权威**，mxl/mid 是"第一版机器可读"。
- 想量化 OMR 质量，用音频侧的音头数/音域做粗对照（差异大 ≠ 必然 OMR 错，转谱模型也会漏软音）。
- 时长对不上先算**变速**：谱面的 `q = X` 标记可能不止一个，还有 rit/accel。

## 7. 用谱当答案，给转谱通道"音符级"打分（DTW 对齐 + 两个对照）

拿到真值谱后，就能第一次给出**定量**结论。做法与**必须配的两个对照**：

**流水线**：谱面事件 `(绝对四分音符, MIDI)` ↔ 通道事件 `(秒, MIDI)`；用 12 维 chroma 做 DTW
把"通道秒轴"映射到"谱面四分音符轴"；再按"同音高 + 时间差 < tol（四分音符）"贪心一对一，算查准/查全/F1。

### ⛔ 五个坑（全是"仪器没验就先读数"，实测踩过）
1. **`librosa.sequence.dtw` 返回的 `wp` 形状是 `(路径长, 2)`，不是 `(2, 路径长)`**。
   写 `wp[0]`/`wp[1]` 当两行用 ⇒ 拿到的只是"第一个路径点"这个二元组，轴全错、映射越界。
   正确：`wp[:, 0]`（=X 轴）/ `wp[:, 1]`（=Y 轴）。
   **判据：两条不同输入给出完全相同的数字 ⇒ 一定是代码 bug。**
2. **⚠️ 最贵的一个：DTW 的时序特征必须"带时值"，不能只用音头脉冲。**
   若 chroma 只在 onset 处置 1（其余列填常数），稀疏脉冲会让 DTW 走出**线性漂移**的时间轴。
   实测：全片最优全局偏移 δ 从 t=0 的 **−1.8s** 单调变到 t=340s 的 **0.0s** ——结果把好通道判成瞎猜。
   改成**持续 chroma**（每个音在 `[onset, offset)` 上持续 +1，逐列归一）后，δ 全片恒定 **−0.2s**，
   同一通道的 F1 从 0.29 跳到 **0.81**。
   **自检（必须做）**：分段（每 20–40s）扫"最优全局时间偏移 δ"并打印/画出来；
   **δ 随进度单调漂移 ⇒ 先修对齐器，再读数。**
3. **bin 分辨率必须与该谱的时间尺度匹配**。太粗会把时间精度抹掉（实测 N=1200 时理想通道只有 0.389；
   `N≈4000`、平滑 ~9 bin、cosine → 0.98）。经验：`N_bin ≈ 8 × 四分音符总数`（492 四分音符 → 4000）。
4. **chroma 空列必须填常数**（否则 cosine 距离 NaN，DTW 直接抛 `cost matrix C has NaN values`）。
5. **平滑窗要按"时间"而不是"bin 数"统一**——两轴 bin 时长不同时用同一个窗宽会过平滑。

### ✅ 两个必跑的对照（不跑就等于没有结论）
- **理想通道对照**：内容 = 谱面本身，时间 = 一条平滑随机速度曲线（`dt/dq = 60/BPM`，BPM 波动 ±25%）。
  它必须拿到接近上限的 F1（本谱 **0.86**）。**拿不到 ⇒ 是对齐器的锅，别去解释通道分数。**
- **洗牌底线（chance floor）**：把该通道的**时间洗乱**、保留音高多重集与事件数，重跑同一条流水线。
  修好对齐器后本谱底线只有 **0.08–0.12**（谱事件稀疏：每音高约 0.08 个/四分音符）。
  ⚠️ **底线若高到 0.7，那本身就是对齐器坏了的症状**（时间轴被压缩，什么都"匹配"）。
  ⇒ 只有 **`F1 − 底线`** 才是有效信号。
- **每条通道必须各自对齐自己**（含洗牌），不要共用一条时间轴——否则分不清"通道差"和"对齐器差"。

### 读结果时的关键区分
- **粗时间尺度**（把进度切 10–25 段，逐段比音级直方图，r≈0.9）说明**和声内容对**。
- **音符级 F1** 说明**每个音落在哪一刻**。两者是不同问题。
- 报数时必须给：`事件数 / 覆盖几个键 / tol / F1 / 洗牌底线 / 提升`。只报 F1 会被底线骗。
- **容差曲线比单点 F1 有信息**：视觉类通道常常"低容差就很高、然后饱和"（时间准、覆盖有上限）；
  音频类常常"低容差很差、随容差一路爬"（覆盖全、时间糊）。
- ⚠️ **别把"互补"自动当成"融合能涨"。** 实测（钢琴项目 grade_fusion.json）：视觉 F1 0.807、音频 0.605、
  **并集 0.797、交集 0.809**（tol=0.22s）；并集只在 tol≥0.72s 才反超视觉（1.5s: 0.872 vs 0.858）。
  ⇒ 融合净收益 **+0.002~0.014，可忽略**。**原因：音频的时间误差(~0.3–0.5s) 与容差同量级**，
  补进来的音**真阳与假阳等量**。**先问一句"最差的通道，其时间误差是否已小于你打算用的容差？"
  若否，融合不涨。** 结论：**单通道够好就别融合**，省掉一整条支路。
- **查全上不去时，先分清"漏读"还是"对不齐"**：取漏掉的谱面音，检查**该键在该时刻 ±0.5s 内有没有通道信号**。
  本项目 624 个漏音里 **80.1% 有信号** ⇒ 缺口主要不是读取，而是**时间对不齐**（演奏 rubato + **真值谱自身(OMR)的时值误差**）。
  ⇒ **天花板有一部分在"尺子"上，不在被测通道上**；要把它做实只能换更准的真值（PDF 原件/人标抽样）。

## 8. 若"视频"其实是 MIDI 渲染器：**别拿它当实拍，直接读键盘**

先花 10 秒抽一帧看一眼。**Synthesia 式可视化**（底部一条固定渲染的钢琴键盘 + 上方下落矩形 tile）
意味着视觉信息是**完备**的（音高/音头/时值都在画面里），比真实演奏视频容易一个量级。
（判据：键盘是静止的、几何规整、键会变色；tile 是圆角矩形瀑布。）

1. **先做"逐像素时间标准差"图**（全片抽帧算 `std(R−G)`）——**键光覆盖条画在哪一段会直接显形**，
   比逐带试阈值快得多。
2. **黑键、白键要分开定判据**。常见大坑：某指标对白键**恒等于 0**（本项目的 `S>60 & V>150` 对
   白键饱和度上界 54）。**白键改用 `R−G`、取样带取白键"下部"（黑键遮挡不到的区段）**，
   池化直方图会呈**教科书式双峰**（中间一段真空）⇒ 阈值几乎不用调。
3. **用键盘标定文件拿每个键的 x 中心与键宽**，逐键开窗（黑键窗口窄、白键窗口宽），别按整幅图取平均。
4. **覆盖率别只看"有几根键有信号"**：先算谱面**逐键事件数**——若谱本身在 B 大调，
   白键只有 E/B/F 会被用到，"只看 20/52 白键有信号"是假警报。
5. **判据验证的最快办法不是对谱，而是"逐键事件数"**：视觉逐键事件数 / 谱面逐键事件数
   若稳定在同一个比值（本项目 0.82–0.88），说明**内容基本对**；此时若 F1 仍低，
   一律先怀疑**时间对齐**（回到第 7 节坑 2 的自检）。

## 9. 纯视觉自举：**不看谱**，把键态直接变成 MIDI（渲染器视频的正解）

若第 8 节确认了是 Synthesia 式渲染，那么**不需要任何谱**就能出 MIDI —— 键态本身就带
**音高 + 音头 + 时值**三样。本项目实测：事件 2212、覆盖 78 键、**谱面用到的 71 键覆盖 98.6%**、
音级分布与真值谱 **r=0.9991**、**onset 自相关主周期 85.7 BPM vs 谱面主 tempo 84**（不需要外部节拍信息）。

**做法**：对每个键取二值"按下"序列 → `diff` 找上升/下降沿 → 合并间隔 `≤3 帧` 的闪烁断点、
丢掉 `≤1 帧`（<33ms）的噪声段 → 每段 `(t_on, t_off, midi)`。写 MIDI 时**直接用绝对秒**
（`pretty_midi` 按 tempo map 落 tick，回放时长不变）；要出**谱**再按估计的全局 tempo 量化到 16 分栅格。

**自举的校验只能靠自洽性**（无真值）：① 谱面用键覆盖率；② onset 自相关 BPM 是否落在合理区间；
③ 与任意可得真值谱的**音级分布相关**（**只用它评估，不参与生成**）。
精确度（音符级 F1）仍然只能靠第 7 节那套（拿谱当尺子）。

**两个必查的软肋**：
- **重复音**：同键快速连击，若渲染的 tile 挨得近，可能被并成一个长段 ⇒ 少报事件（查全掉）。
- **合并不当**：`max_gap` 太大吞掉休止、太小把一音裂成两音。本项目 `min_frames=2, max_gap=3`（30fps）可用。

**方法论**：自举出的 MIDI **不要**再用它去"验证"自己（同源自证）；要独立校验就合成音频与源音轨对齐，
或（更强）用独立来源的谱做第 7 节打分。

### 出事率最高的两个"谱面落盘"坑（实测，都是静默错）
1. **别做"顺序去重叠"**：想"避免同位置冲突"，写 `if o < prev_end: o = prev_end; prev_end = o + d` ——
   密集钢琴曲里音重叠极多，**每遇到重叠就把后面全部前推**，把整条时间轴**串行化**。
   实测：真实 500 四分音符的曲子被撑成 **1616**（+223%），而且**写入时不报错**。
   正解：**按 onset 聚成 `Chord`**（同 onset 的多音合成一个和弦），onset 之间自然不冲突。
2. **别调 `stream.makeMeasures()`**（写 MusicXML 前）：实测它让**回读**跨度从 504.2 涨到 **688.8（+37%）**，
   内存里的值却是对的 ⇒ 典型的"写前对、落盘后不对"。**直接写 Part**，music21 的 writer 自己会分小节
   （回读 127 小节，正确）。**自检：写完必须 `parse` 回来核 `highestTime` 与真值相符。**
   附带坑：若为"避免重叠"把时值截断到下一 onset，会产出 **2048th 音符**（比 64 分还短）⇒ 导出直接抛
   `Cannot convert "2048th" duration to MusicXML`。

### 边界（诚实标注）
- 这是一次**单声部最佳努力**的量化：按 onset 聚和弦、**不区分声部/手别**；被延音掩盖的同键重复音可能被并成一段。
- 想得到**可演奏的成品谱**，正确链路是 **MIDI → MuseScore 自带 MIDI 导入**（含量化/声部分离），
  不要在 Python 里手搓记谱排版。

## 10. 把第 8/9 节套到"别的视频"：先假定它**不是**同款渲染

四条视频可以长得**完全不同**，而标定脚本仍可能各自报 `valid=True`（自校验只验黑键 7 周期图案，**不验键盘带对不对**）。
**上第一条视频前，先花 10 分钟做这三件事**（本项目实测踩全了）：

1. **抽帧肉眼看**：键盘是"固定渲染的平面键盘"还是"3D 透视键盘"？有没有**手**？（本项目 v2 无手、
   v1/v0 都有写实半透明的手、animenz 是真拍。）渲染器不同 ⇒ 读数带、判据、颜色全都得重定。
2. **逐像素时间标准差图**（第 8.1 节）：亮点会告诉你"信号到底落在哪些行"。**注意手也是高方差**，
   它会在图上呈**竖直尖峰**，和键光长得像；本案 v1 的尖峰**主要是手**。
3. **逐 y 带扫描**：先抽一次"每个候选 y 带 × 每个键"的时序（`cache/keylight/<tag>_bands.npz`），
   之后离线扫带，别为每个带重解全片。

### ⚠️ 三个必踩的坑
- **`pitch_map()` 把最左白键写死当 A0(21)**。这份代码对 v2 恰好成立（v2 最左就是 A），
  但 v1 最左是 C、v0 最左是 B ⇒ **整条视频平移几个半音**而不报错。**音高锚点必须另定，见下。**
- **手会冒充"按键"**：皮肤 `S` 高、`V` 高，**正好触发** `S>60 & V>150` 这类"键亮"判据 ⇒
  SAT 通道在有人手的视频上会变成**手部检测器**。判定办法：看该通道的活跃是否**只集中在两个手位**、
  且与音高的相关性随"音高平移"不敏感。
- **音头自相关前必须先把 onset 排序**：不排序时 `onsets[-1]` 可能是小的，直方图数组被截短、
  大量 onset 被 `min(n-1, ...)` **夹到最后一格** ⇒ 造出**假周期**（本案 v1 假报 162.2 BPM，排序后是 50.0）。

### ⛔ 头号陷阱：**指标本身会骗你**（本案被坑两次，务必先拿正对照验仪器）
"每键活跃度"看起来随便算都一样，实测**不同合理指标给出的最佳 base 天差地别**：
同一批 v2 数据，用 A 指标峰值在 21（真值）、B 指标在 20、C 在 23、D 在 17。
⇒ **凡"锚点/交叉"类读数，必须先用 v2（已知 base=21，无手）当"正对照"跑一遍**，
**仪器能在 v2 上自己找回 21，才有资格去读 v1/v0**。否则读到的是指标伪影，不是钢琴。

最坑的一个伪指标：`中位数 + 3×MAD`（稳健阈）当"按键强度"。
**从没被按过的键，MAD≈0 ⇒ 阈值≈它自己的中位数 ⇒ 会被判成"一半时间在按"（假活跃 ~0.5）**，
整张音级相关图**被反转**（它给真值 base=21 的 v2 打出 −0.646 = 铁证）。
**判据**：任何"稳健归一"法都要先检查"常数键"（方差≈0 的键）会不会被它误点亮。**本案唯一验过的仪器**是下面的固定门。

### ✅ 免费又可靠的**八度锚点**：异源交叉（视觉 vs 音频）——但用**验过的固定门**
不需要任何真值。做法：算"每键活跃度"（沿时间平均），把视觉的**键序 index** 与音频钢琴卷的
**MIDI bin** 在平移 `base`（`midi = base + index`）下做相关，扫 `base`。
**通道门用本案在 v2 上验过的固定门**（别用 Otsu：RG 重尾会把门落到数据下方，SAT 的 Otsu 常=1.00 过严）：

```
R = np.where(is_black[None,:],  blkS > 0.25,  whtLO > 20)   # 黑键用 SAT，白键用 R-G
```

| 视频 | 锚点 base | 交叉 r（固定门） | 占空比 黑/白 | 结论 |
|---|---|---|---|---|
| v2（正对照，真值 base=21） | **21** ✓ | 视觉 vs 音频 **+0.985**、vs 谱 **+0.990** | 6.4% / 1.7% | **可读**（无手） |
| v1 | 24（=C1，锚点能定） | 视觉 vs 音频 **−0.030**、vs 谱 **−0.029** | **19.3% / 19.8%** | ⛔ **不可读** |
| v0 | 23（=B0，锚点能定） | 视觉 vs 音频 **−0.724** | **22.3% / 0.1%** | ⛔ **不可读**（白键通道全死） |

**关键醒悟**：用"扫参数最大化相关"的方式能在 v1 上凑出 **r=0.72**、在 v0 上凑出 0.73 ——
**那是把门/带调到正好贴合"手"和"全局光效"得到的**，不是读到真按键。
换成在 v2 上验过的固定门，v1 立刻掉到 ≈0。**"能凑出高相关"≠"读到了键"**，这是第 10 节的中心教训。

**锚点怎么定（本案可靠路线）**：
- **音级**：标定 `names`（自校验 `pattern_match=1.0` 的 7 周期图案）给出最左键名 ⇒ 定 `base mod 12`（v1=C⇒24、v0=B⇒23）。
- **八度**：物理键盘窗口 `21 ≤ base ≤ 109−NK`，把所有 `base≡base mod 12` 的候选夹进合法范围（多数视频只剩 1 个）。
- **异源交叉**只当**佐证**，且**必须用固定门**；交叉与音级矛盾时以"锚点自定 + 占空比异常"判不可读，别硬凑。

### 判"这条视频能不能读"的验收线（本案口径，已修正）
不看"能不能凑出高 r"，看**两个硬指标**：
1. **占空比**：真渲染键盘的键态稀疏（v2：黑 6.4% / 白 1.7%）。若黑/白占空比都 **≳15%** ⇒ 通道在追**手/光效**，不是键（v1 黑白都是 ~19%）。
2. **固定门下的异源交叉 r**：**≳0.6** 才算可读；**≈0 或为负** ⇒ 不可读。
- v1：占空比 19%/19% + 交叉 ≈0 ⇒ **不可读**（写实的半透明手覆盖键盘，SAT/RG 全变成"手部检测器"）。
- v0：白键通道占空比 0.1%（**全死**）+ 黑键 22%（谱线/手/高光）⇒ **不可读**。
- ⇒ **纯视觉自举只在"无手的平面渲染键盘"上成立（v2）**；凡有写实手盖在键上的视频，键态通道被手污染，**套不过去**。
