# 音乐库元数据/歌词异常取证与修复

交付物不是"我查了一下"，而是：**可复现的证据 + 根因归属（数据 or 上游代码）+ 双向验证
+ 一份带复选框、用户勾了才改的清单**。

## 第 0 步：先确认"你在读哪个库"（最容易翻车的一步）

用户说"播放器里某某歌不对"时，**不要**默认去读源码目录的 `data/`。常见形态：

- 运行中的播放器是**便携部署版**（另一个盘符/目录），它的数据目录才是活的；
- 源码目录的 `data/library.json` 是**陈旧快照**，曲目数都可能对不上。

判据（按顺序做）：

1. 找监听进程：控制协议端口（此处 43121）→ `netstat -ano | grep 43121` → 拿 PID；
2. 用 PowerShell `Get-CimInstance Win32_Process -Filter "ProcessId = <pid>"` 看
   `ExecutablePath` / `CommandLine`（⚠ PowerShell 工具 stdout 常为空，**必须 `Out-File` 写文件再 Read**）；
3. 进程所在目录下的 `data/` 才是活库；对比两边 `library.json` 的 `mtime` + 曲目数确认。

同时把三个库列清楚：**原始音频源（有真实 ID3，是 ground truth）→ 归档库（DB）→ 播放器库**。
只要原始音频还在，每首都有真相可查，这决定了修复能自动化到什么程度。

## 第 1 步：只读取证（不写一个字节）

```python
sqlite3.connect("file:/abs/path/db.sqlite?mode=ro", uri=True)   # 只读，避免锁库/误写
```

- **用哪个解释器**：跑归档库的脚本要用**归档项目自己的 venv**（它才有 av/mutagen 等依赖）；
  用播放器 venv 会 ImportError。这条常被忽略，浪费很多时间。
- **拿文件标签反查 DB**：`mutagen.File(path)` 取 title/artist/album，逐字段与 DB 比对。
  分类：① 值不同但都"正常"→ 内容矛盾；② DB 里有汉字而文件标签没有 → **疑似被乱码化**；
  ③ 文件无标签 → 无法校验（高风险区，务必单独计数）。
- **歌词绑定核查**：比对"曲的 artist"与"词的 artist"，**先去括号/译名/多歌手分隔符**再判；
  一边拉丁一边 CJK 的差异多半只是译名，**单独成类**避免误伤。

## 第 2 步：分清"数据脏"还是"上游代码把数据改坏"

这是本类任务的核心判断。**若文件标签是对的、只有 DB 是错的 ⇒ 是上游代码 bug，不是数据老化。**
去上游项目搜：乱码修复函数 / 去重合并逻辑 / 字段补全逻辑。

看代码时重点找这两类反模式：

1. **择优函数带有偏的计分**：例如"重解码后得分更高就采纳"，而计分只给 CJK 加分、
   不给带变音符号的拉丁字母（`å`/`é`/`Ø`）加分 ⇒ 正确文本反而输给乱码版本。
   - 症状特征：**中日文没事、只有外文歌乱码**（因为 CJK 无法 latin1 编码，函数直接放弃）。
2. **匹配/合并只看一个字段**：如歌词只按 title 匹配不看 artist（歌手当排序权重而非过滤条件）；
   重复曲目合并时把"另一方"的字段无条件借过来 ⇒ 串专辑、串歌手。

**乱码方向要实测，别猜**。用 `repr` + 逐字节验：

```python
'é'.encode('utf-8').decode('gbk')   # -> '閘'  ⇒ 说明是 UTF-8 字节被按 GBK 读出
v.encode('gb18030').decode('latin1') # 反向还原
```
常见方向有 `utf8→latin1`、`utf8→gbk`、`latin1→gbk`，**反向公式各不相同**。

**第四种族：「ASCII + NBSP 被 GBK 读成纯汉字」**（2026-09-23 实测发现）。
打标签工具有时用**不换行空格**（NBSP, `\xa0`）代替普通空格：`C\xa0O\xa0N\xa0F…`。
被按 GBK 解码时每个 `\xa0+字母` 字节对折成一个 **GBK 扩展区生僻字（首字节恰好 0xA0）**，
得到 `C燨燦燜燛燬燬營燨燦` —— **以汉字为主、拉丁占比仅 0.1**，"拉丁占比 ≥0.65"类检测臂
永远抓不住。反解公式：`garbled.encode('gbk').decode('latin1')`（每个非 ASCII 字符
反解后**恰好是 `\xa0`**）。判乱码的安全闸门：含 ≥2 个 CJK + 反解全为 NBSP +
反解结果全为可打印字符 —— 真 CJK/全角文本（`遥か`/`廉`/`！`/`～`）反解出 `Ò`/`£`/`¢`
等不可打印字符，自动排除。

**改乱码检测代码后，必须做「全库 HEAD 对照」证明行为变化面**：
把库里全部字段分别跑新旧两版修复函数、逐字段 diff。
本机实测对照结论：新臂只新增 2 处变化、均为正确修复 ⇒ 可自动修。
（曾暴露的"既有函数本来就改坏"上游 bug——`惑星VORTEX`→`´b¬PVORTEX` 等
big5/cp932 摇奖臂误伤——**已于 MuseArc d778530 修复**：`_repair_mojibake` 改用
结构判据，只接受"反解字节构成可证明还原形态"（latin1 全拉丁字母 1:1，或完整
合法 UTF-8 流）；`_looks_mojibake` GBK 臂共用判据，因为误判会让导入器把标签值
**置空重推导**。全库 2730×3 非空白改动 = 0。遗留不可判别类：GBK 码位恰为合法
UTF-8 拉丁字母的字（猫=C3A8=è）夹在拉丁词中与真乱码同形，全库无存量。
动手前仍要分清"我引入的"还是"本来就有的"（`git stash` 重跑对照即知）。）

## 第 3 步：修复必须做**双向**验证

只证明"能修好乱码"是不够的，**必须同时证明"不会把正确文本改坏"**——因为这类 bug 的
本质就是"修复函数主动搞坏正确数据"，只测单向就会写进一个新的同类 bug。准备两组样本：

- **防破坏组**：一批正确的多语言文本（含带变音符号的），断言 `repair(x) == x`；
- **可还原组**：一批已存在的乱码 → 期望的正常值，断言 `repair(乱码) == 正常值`。

再补**回归测试**进上游仓库 + 跑**全量测试** + `ruff check`。同时记得**同步项目文档**
（导入流水线说明那类），很多仓库有"改逻辑必同步文档"的惯例。

⚠️ **该跑 `ruff check` 就跑它，不要顺手跑 `ruff format`**：若 CI 只做 lint 不做 format check，
说明仓库并未 format 过，跑一次 `ruff format` 会引入大片换行/空行噪音污染 diff。
（真跑了，可用 difflib 按"去空白后是否相同"逐块还原。）

## 第 4 步：交付"勾选清单"，不要静默批量改

大范围修复**永远不要**直接批量执行。生成 `fixlist.md`：

- 顶部：汇总表（类别 / 条目数 / 说明），并单列"已完成的代码修复"与"待你勾选的数据修复"，避免混淆；
- **批量项**（`- [ ] **【批量】以上全部…**`）+ 逐项明细（`- [ ] \`id\` · 文件名` + 缩进子行给 `旧值 → 新值`）；
- **误报单列**（如译名差异），并注明"一般不用动"；
- 末尾给**需要用户拍板的决策项**（修复范围 / 同步策略 / 解绑语义）。

勾选驱动的执行脚本要：**先备份 DB** → 同一事务内只改勾选项 → 改完复核。
留痕优先：能写进下游自带的 `undo_actions`（`action_type` + `rollback_values`）就别只靠备份。
用户要"彻底断"也要"可回滚"时，两者不冲突 —— 数据彻底断、留痕表留旧值。

## 第 5 步：把修复同步到下游播放器（**最容易漏掉"只增不删"**）

### 5.1 先判断下游在不在运行

**看控制端口是否监听**，不要看进程名 —— 本机实测 `pythonw.exe` 里那个常驻 PID 其实是
`C:\Program Files\Common Files\HFComponents\pythonw.exe`，属 **雪藏 HsFreezer**
（游戏冻结/进程优化工具；`HFComponents` = **H**s**F**reezer **Components**），
**与火绒/杀软无关**，也不是目标程序。
判据：`netstat`/探测 TCP 端口 + 看数据文件 `mtime` 是否新鲜。

- **在跑** → 优先走它自己的控制协议（导入/删除命令），由它维护内存态与索引。
- **没跑** → 走**离线**：直接构造它的 service 层（**先确认无 GUI/Qt 依赖**），
  产出与运行时**完全同构**的 JSON。比手搓 JSON 安全得多。
  ```python
  svc = LibraryService(LibraryStore(data_dir), MetadataService())
  svc.load(quick=True)          # quick 跳过缺失文件/去重等磁盘检查
  svc.import_muse_playlist(export_path)
  ```
- 无论哪条路，**先对数据文件副本跑一遍全流程 + 校验**，再动正式库。

### 5.2 四条必须背下来的语义（都是本机实测踩出来的）

1. **导入只增不删。** 播放器的歌单导入删除逻辑只作用于"本次从**同一个**歌单移除的曲目"，
   且还要过"孤立曲目"判定；新建歌单导入时旧集合为空 ⇒ **什么都不会删**。
   ⇒ "全量重同步" **不包含**清理，删除必须单独做。
2. **`"全部歌曲"` 是派生清单**，由规范化函数从曲目全集重建。
   ⇒ 让一首歌真正消失的唯一安全通道是
   `remove_track_from_playlist(ALL_SONGS_ID, track_id)`（内部走 `_remove_track_globally`）。
3. ⛔ **不能用 `delete_playlist()` 清理导入产生的"脚手架歌单"**：它按"孤立曲目"口径
   连坐删歌，而该口径**排除 `all_songs`** ⇒ 会把只被 `all_songs` 引用的大量曲目一起删掉。
   正确做法：`svc._playlists.pop(pl.id)`，并把 `active_playlist_id` 回收到 `all_songs`。
4. **导入函数内部会无条件 `save()`** ⇒ 不存在"预演不落盘"。预演阶段只能做只读统计，
   别调导入。写完校验：缺 N / 多 N / 歌单悬空引用 / `all_songs` 是否等于曲目全集 / 活动歌单是否有效。

### 5.3 删除范围必须先做"交叉引用分析"给用户看

删 N 首前，先算清楚它们**还躺在用户哪些真实歌单里**（排除"待删除"这种本就为删而建的表），
把那几首歌名逐条列出来给用户确认。用户最可能在这里推翻自己的"删"决定 —— 本机案例：
164 首里有 3 首同时在用户精心维护的小歌单里（其中 1 首正是用户先前标记"信息有误要修"的歌）。

另：上游的"已删除"通常只是**软删除标记**（tombstone），文件还在、可 `restore`。
所以"删"和"改好"不是二选一 —— **先问用户要不要保留**，保留就走 restore 让它随修复一起传播。

### 5.4 会话/统计的连带影响

- 删歌前查 `session.json` 的 `current_track_id` / `current_playlist_id` 是否仍存活（否则下次启动
  是空会话）。
- 删歌**不会**同步清理 `playback_stats.json`（只动曲目表与歌单）。残留统计项无害，
  但别报告成"统计已清理"。

## 第 6 步：存量回扫（历史已绑定的数据错了怎么办）

上游匹配规则修好后，**历史遗毒仍在**（旧的错绑定不会自己消失）。回扫 = 拿新标准重判存量。
分四拍：**只读探针 → 分桶扫描 → 逐条正向取证 → 改绑 + 双向核对**。

### 6.1 先把"存量"的量级和分布摸清

不要一上来就扫全库。先单独跑一个只读探针，按 `match_method`（或等价的来源标记）分组计数，
确认**目标人群**规模，再决定策略。⚠️ 数量会随上游写入漂移（本次同一批数据前后测到
1487 / 1482 / 1477 三个值）—— **引用数量必须带时间戳**，别当常量。

### 6.2 分桶，而不是"查出错就改"

扫出候选后按**证据强度**分桶，每桶单独定策略。本次实际分桶（1482 条）：

| 桶 | 含义 | 策略 |
|---|---|---|
| `D_正常` | 找不到问题 | 不动 |
| `C_保留` | 同名 sidecar 但歌词 `[ar:]` 与曲目歌手矛盾 | **通常要保留**，见 6.3 |
| `E_待查` | 歌名不同但歌手相容 | 多为 `feat.` 写法差异，不动 |
| `Z_已删` | 曲目已软删除 | 不动 |
| `A_改绑` | 另有更优候选 | 改绑 |
| `B_解绑` | 确认是别人的歌词 | 解绑 |
| `F_待人工` | 有矛盾但证据不足 | 只列不自动改 |

### 6.3 ⛔ 只按**正向证据**动手 —— 这条把 8 条误改砍到 1 条

"歌手不符 ⇒ 解绑"是**错**的。`[ar:]` 里的名字与曲目歌手指向**同一个人/同一录音**是常态：

- **跨字形同一人**：`磯村由紀子` vs `矶村由纪子`（日文汉字 vs 中文简体）
- **组合 vs 成员**：曲目挂组合名 `後ろから這いより隊G`，歌词 `[ar:]` 写三位声优
- **角色名 vs 演唱者**：`鞋儿破帽儿破` 的 `[ar:]` 写"济公"（剧中角色），
  但**歌词正文第 6 行自己写着** `[00:00.00]鞋儿破帽儿破 - 何纪光`
- **专辑一致**：`[al:]` 与曲目 album 完全相同时，大概率就是同一版本

⇒ 解绑必须**额外**要求：**该歌词在它自己的目录里另有同名曲目**（即"它是有主的，只是主不是你"）。
本次这条硬约束让 8 条拟解绑只剩 **1 条** 成立。

⇒ 反过来，**改绑**才是更常见的正解：若库里存在 `[ti:]` **和** `[ar:]` 都与曲目对得上、
且**当前无任何绑定**（自由歌词）的候选，改绑它 —— 零副作用，比"解绑留空"好得多。

### 6.4 歌手相容判定：按**空白分词 + 子集**，不是交集

归一化函数通常已把 `/、×,;｜|&` 等分隔符**折成空格**。此时再按分隔符 split 是**死代码**，
必须改用空白分词。且语义要用**子集**：

```python
return smaller <= larger      # 子集：Feint/Veela/Boyinaband ⊇ Feint/Boyinaband/Veela ✓
# return bool(a & b)          # 交集：Taylor Swift 与 Taylor Dayne 因共享 Taylor 误判相容 ✗
```

还要**先去括号再归一化**（否则 `初音ミク` 与 `初音未来 (初音ミク)` 会因括号内容被删而不相容）。

### 6.5 落库与留痕

- 改绑走 App **自己的手动口径**（本次是 `set_primary_lyrics_for_track`，内部写
  `match_method='manual'` + `confidence=1.0`）。好处：语义上标记"人为裁决"，
  **后续自动匹配不会再来覆盖**。
- 每条都写一条 **undo 记录**（`undo_actions` + 与 App 自身操作**完全一致的 payload 结构**），
  这样 App 里能直接回滚 —— 用户要"数据正确"也要"可回滚"时两者不冲突。
- 脚本内做**前置断言**（当前值 == 计划里的旧值，否则中止），避免在已被改动的库上盲写。
- ⚠ **别把"改绑"说成"旧词变孤儿"**：这类 App 的改绑实现（如 `set_primary_lyrics_for_track`）
  通常只是把该曲**所有**链接置 `is_primary=0`、再把新词置 1，**旧歌词链接仍挂在原曲上**
  （仅降为非主词）。要真断链得另调 `unlink_lyrics_for_tracks([...])`。
  落库后**回头读一次**确认链接状态（`is_primary` 0/1 各几条）再写报告。
- 结束跑**双向交叉核对**：DB 侧读一次、下游 JSON 侧读一次，逐字段比对 + 确认旧引用
  **在所有字段里都不再出现**（`json.dumps(整条记录)` 全文搜一遍最稳）。

### 6.6 同名字 sidecar 是**最强信号**（上游规则可顺带加固）

同一目录下文件名与曲目同名的 `.lrc`，应**直取**为主词，优先级高于"按 `[ti:]` 标题匹配"
（标题匹配会被"剥括号"归一化坑到：`Faded (即刻电音版)` == `Faded` ⇒ 跨歌手误绑）。
歌词自身的 `[ti:]/[ar:]/[al:]` 只当**加减分辅助**，**不作为否决条件**——因为
`[ar:]` 是占位符（`未知歌手`/`various artists`）或唱片公司名的情况很常见，一旦否决会大量漏绑。
给个可用的锚点分：无元信息 0.90 自动绑、全相符 1.00、歌手矛盾 0.45 转人工。

⚠ **但"同名"必须分两档，否则会静默绑错版本**：文件名与标题都常带版本标记
（`(Live)`/`(Remix)`/`(2)`/`(高音质版)`），而这类"归一化"实现普遍会**把括号内容一起剥掉**
（`Faded (即刻电音版)` → `faded`、`红昭愿 (高音质版)` → `红昭愿`）。一旦只按归一化同名判"同名"，
同目录的 `X.lrc` / `X (2).lrc` / `X (Remix).lrc` 就**同分抢同一首曲目**；
更糟的是候选枚举常用 `Path.rglob("*")`（**不排序**，顺序=文件系统目录项），
于是"谁先被处理谁成为主词"⇒ **结果不可复现**，且先到的若过阈值会**静默绑定、不进审查**。
本机实测库内同目录同基名 34 组 / 70 条，其中 10 组是多版本共存。
**正确做法**：文件名 stem 与曲目标题**逐字同名**（忽略大小写）才给直取分；
仅归一化同名的一律压到阈值以下转人工。存量排查时也要专门查这一类——
**"歌手相同、只有版本标记不同"的错绑，用"歌手矛盾"筛法一条都抓不到**（判据改为：
逐字同名的 sidecar 却不是主词，且与当前主词正文相似度显著 <0.95）。

⚠ **相似度过滤别用 0.95，用 0.9，且要认识两类假阳性**（2026-09-23 整类重扫实测，
20 组候选里真错绑只有 4 条）：
- **重复文件序号**：`X (2).lrc`/`X (3).lrc` 是去重工具的副本编号，正文 sim≈1.0 ⇒ 不是错绑；
- **译名字幕变体**：`courage.lrc` vs `courage (勇气).lrc`、`SAKURA` vs `SAKURA (樱花)`，
  正文 sim 0.97+ ⇒ 同曲不同文件名，不是错绑；
- **同曲不同歌词制作版**（`踊り子` kana 注音版 vs 普通版，sim 0.6）：**必须看正文再定**，
  别自动改——可能当前版反而更好（带 kana/行数更全）。
- 另有独立一类：**"该绑未绑"**（曲目无任何主词、但逐字同名歌词已在库）——
  这是"新增绑定"不是"修错绑"，单独记 todo，别混进修复批次。
- 改绑守卫查"新主词是否被占用"时，**必须排除已软删曲目**
  （软删的重复条目仍持有 is_primary=1 链接，属正常残留）。

## 易踩的坑清单

- PowerShell 工具 stdout 恒空但命令**确实执行**了 → `Out-File` 再 Read，别重复跑。
- 本机 git 要用用户自装的 Git（先 `export PATH="/e/System_Programes/Git/cmd:$PATH"`），
  否则 push 弹交互窗卡死。
- 曲库相关个人路径/清单**绝不入仓库**；探查脚本放已被 gitignore 的 `temp/`。
- 大范围扫描用 `run_in_background`，别占着前台超时。
- ⛔ **Git-Bash 风格路径不能直接喂给 Windows Python**：`Path("/e/Foo")` 不是 `E:\Foo`，
  而是"当前盘符下的 `\e\Foo`"⇒ 会**加载到空库（0 首）并往错处写出一个假库**。
  传路径一律用 `E:/Foo` 或 `E:\Foo`。踩到时立即用找出的散落文件核对并清理，别让它留在盘上。
- **备份与临时副本要分清，但都别擅自删**：备份（DB / 数据文件）保留到用户自己确认；
  连"预演用的副本"这类中间物，删之前也先想一下用户会不会想留。
- 判断进程身份要看**可执行文件路径**（WMI `ExecutablePath` / `ps -W`），不能只看进程名。
  本机实测：`C:\Program Files\Common Files\HFComponents\pythonw.exe` 是**雪藏 HsFreezer**
  （游戏冻结/进程优化工具，`HFComponents` = **H**s**F**reezer **Components**），
  **不是杀软**。作者为免被当普通 python 杀掉，故意把进程描述改成 System、改图标、弃签名，
  所以**看起来极可疑**。反查用 `reg query "HKCU\SOFTWARE" /s /f "HsFreezer"`（`HFComponents`
  自身注册表零残留）；或直接读该目录的 `readme`（GBK）。
  ⛔ 该 readme 里作者**推荐**火绒当杀软 ⇒ 搜到"火绒"字样**不等于**进程归火绒（踩过）。
- **同一文件绝不在同一批里发两条 Edit**：只落一条，另一条**静默消失**。必须串行。
- **别把 `git show HEAD:<file>` 导出到项目外目录再跑 ruff**：读不到 `pyproject.toml`，
  `ruff format --check` 会报"0 差异"这种**假象**。要对照必须放进项目内（用完删掉）。
- 路径字段常有**双份语义**：`storage_relpath` 是分片归档路径（`data/tracks/69/…`），
  要拿"原始目录/相对路径"得看 `source_relpath`。用错会让"同目录"分析全部落空。
- 报告里"跨表/跨库数量对不上"时先怀疑**口径**（字段数 vs 曲目数、存活 vs 含已删、
  同一实体在多表各记一次），本机踩过"3 首 X;X"实为 2 首曲目的字段计数。
