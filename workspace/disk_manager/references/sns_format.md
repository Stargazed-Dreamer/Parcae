# SpaceSniffer .sns 快照格式（逆向笔记）

> 逆向验证基线：本机 C 盘快照（67,676,974 字节，852,241 条记录 = 1 卷 + 706,340 文件 + 145,898 目录 + 2 伪记录），
> 纯结构遍历指针恰好走到文件尾、栈恰好清空、0 违例；另对拍 GitHub 参考
> [jerrylususu/SpaceSniffer_Format](https://github.com/jerrylususu/SpaceSniffer_Format) 的 608 字节示例
> （该仓库框架正确但字段宽度有误：称"大小 16 字节/占用 8 字节"，实测 8+4，以本文为准）。

## 记录布局（little-endian，顺序流式）

| 记录内偏移 | 长度 | 含义 |
|---|---|---|
| +0 | 1 | 固定魔数 `0x02` |
| +1 | 1 | 类型：`01`=卷(根) `02`=文件 `03`=目录 `04`=可用空间 `05`=未知空间 |
| +2 | 4 | uint32：Base64 文件名长度 len |
| +6 | len | Base64(ASCII) 文件名（不含路径） |
| +6+len | 8 | int64 逻辑大小（字节）。**目录 = 子树文件逻辑大小之和**；卷 = 卷已用空间（来自卷统计，含 NTFS 元数据，比顶层求和大 ~4GiB，差额是 $MFT 等） |
| …+8 | 4 | uint32 疑似簇尾浪费（文件 = 4096 − logical mod 4096，整簇为 0；目录无明确语义） |
| …+12 | 4 | uint32 Windows FILE_ATTRIBUTE（文件常见 0x20=ARCHIVE；目录 = 0） |
| …+16 | 24 | 3×int64 FILETIME（创建/访问/修改，顺序未细究；目录 = 全 0） |
| …+40 | 2 | **状态字**（little-endian uint16）——⚠ **不是哨兵**，详见下一节 |
| …+42 | 2×k | `01 00` × k：弹出最近 k 个已打开层级 |

## ⚠ +40 状态字（2026-09-24 修订：此处曾被误写成「`00 00` 结束标志」）

绝大多数记录是 `00 00`，但**权限不足的扫描**会混进少量非零值。实测 C 盘快照
（141,644,370 字节 / 1,786,605 条记录）分布：

| 状态字 | 条数 | 典型位置 |
|---|---|---|
| `00 00` | 1,786,478 | 绝大多数 |
| `00 04` | 122 | `Users`、`Program Files`、`ProgramData`、`$Recycle.Bin`、`Recovery`… |
| `00 02` | 3 | `C:\` 卷记录本身、`LCU`、`Package_for_RollupFix~…` |
| `00 06` | 2 | `Windows`、`servicing` |

- **语义尚未确定**。已证伪的假设：与 FILE_ATTRIBUTE 无关（`attrs & 0x06` 命中率 99.6%，
  只是 0 占绝大多数的假象）；也**不代表子树残缺**——这些节点的 size 与
  「子目录 size 之和 + 直属文件大小之和」完全相等。
- 观察到的共性：非零状态字集中在**需要提权才能枚举**的路径，推测是 SpaceSniffer
  对这些条目走了另一条枚举分支并留下标记。

### 曾经的故障形态（别再踩）

老实现在这里硬校验 `data[ne+40:ne+42] == b"\x00\x00"`，结果整份快照在**第一条（卷）记录**
就抛「missing end marker」，表现得像文件损坏。实际：

- 重新导出得到的 `快照C2.sns` 与 `快照C.sns` 字节完全相同（141,644,370 字节），依然失败
  → **不是导出问题**，也不是权限问题
- 放宽这 2 字节后，本机四份快照 **全部精确走到文件尾（`pos == len(data)`）且栈深归零**

结论：**不要对它做等值校验**。真正的结构防线是「魔数 + 类型 + name_len 边界 + pops 栈平衡
+ 精确走到 EOF」。解析器把它记成 `stateful_records`（`parse_sns` 的 meta 字段），纯诊断用途。

### ⚠ 「unknown=0」不等于「扫全了」

另一个陷阱：权限不足的 C 盘快照里 `05` 伪记录仍然是 0，`is_complete` 因此报 True。
但把 **卷记录的 used 减去所有顶层子项之和**，会发现 **74.3 GiB 无法交代**（正常只差 NTFS
元数据 ~4 GiB）——因为 `C:\Windows\WinSxS` 等受保护目录压根没进快照，`Windows` 只有 13.4 GiB。

判断快照可信度的正确姿势是**做顶层对账**，而不是看 `unknown_bytes`：

    gap = volume.used_bytes − Σ(顶层目录 size) − Σ(根级文件 size)
    gap 远大于 ~4 GiB ⇒ 有目录没被枚举，不要拿它排 TOP 榜

## 层级：栈语义（不是缩进、不保证字典序）

- 每条记录（含文件）逻辑入栈；记录尾部的 `01 00`×k 从栈顶弹出 k 层
- 文件/伪记录（04/05）：第 1 个 pop 关闭自己，多余的关闭祖先
- 目录：有子项 → 自身记录 pops=0（由最后一个子项记录的额外 pop 关闭）；空目录 → 自身 pops=1
- **记录顺序不保证字典序**，层级只能靠弹出标记恢复

## 名称编码

- Base64，解码后按 `utf-8 → gbk → utf-16-le → latin-1(replace)` 尝试（本机实测中文为 GBK）
- Base64 中可能嵌入 `\r\n`（MIME 换行）；`base64.b64decode()` 默认 `validate=False` 自动丢弃

## 伪记录（卷的直接子项）

- `04` = 可用空间（卷剩余，**不要**计入已用量）
- `05` = 未知（尚未扫描）空间（=0 说明扫描完整）

## 尺寸口径与对账

- 已用空间以**卷记录**的 logical 为准（含 NTFS 元数据）
- 校验：顶层目录求和 + 根级文件 + NTFS 元数据 ≈ 卷记录值
- 文件大小是逻辑字节（非簇占用），对清理决策无影响

## 快照体积特征

百万级文件的整盘快照 ≈ 67MB（约为盘内容 0.06%），可长期留档做清理前后对比。

## 与 scan_disk 缓存的字段映射

| .sns | scan_disk 缓存 |
|---|---|
| 卷/目录记录 | node（complete=True，mtime=None） |
| 文件记录 | 父节点 `files_top[]` 条目 `{name, size, mtime}`（mtime 格式 `YYYY-MM-DD HH:MM`） |
| 卷名 `C:\` | `scan_meta.path = "C:"`（归一化，--path 过滤用） |
| 04/05 伪记录 | `scan_meta.volume.free_bytes / unknown_bytes`（不进树，避免污染 find/caches） |
| 卷 logical | `scan_meta.volume.used_bytes` |
| —（快照无） | `files/dirs` 子树计数由导入器后序计算 |

导入器：`scripts/parse_sns.py`；缓存写入 `temp/disk_scan_cache/sns_*.json`（`sns_` 前缀避免与 live scan 缓存混用 slug 匹配）。

## 原生负数 size 记录（2026-09-24 C_final 快照实证）

SpaceSniffer 自己会写**负的目录 size**（`<q` 有符号 int64，如 `$Recycle.Bin` = -6,023,437,800），
出现于「扫描期间内容被删/无法完整枚举」的目录（WeType 三目录、$Recycle.Bin 实证）。
解析器**照读不修**：聚合会向上传播负值，属快照原生语义。
对账时注意：此类负值会让「Σ子项」偏小，别误判为解析 bug 或扫描残缺；
`$Recycle.Bin` 的实际内容以可见 `$R` 子项之和为准，负值部分代表未逐条枚举的变动。
