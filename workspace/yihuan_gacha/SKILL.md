# 异环抽卡记录统计 Skill

## 概述
通过 Parcae 后端 API 截取异环游戏窗口，OCR 识别抽卡记录，颜色检测稀有度，图像处理检测骰子点数，清洗后经审核写入最终归档。

## 棋盘类型
- **限定棋盘** — 限时角色/弧盘
- **标准棋盘** — 常驻角色/弧盘
- **弧盘研募** — 武器池（普通抽卡，非棋盘机制，详见下文「弧盘研募池」章节）

## 稀有度判定（2026-10-30 起：权威表优先 + HSV）

**第一步先查 `RARITY_MAP`**（`yihuan_clean.py` 的权威表）：表里有的物品直接用表值，
不跑图像、也不进待复核。只有表里没有的新物品才走颜色判定。

**颜色判定用 HSV 核心口径，不判 RGB 绝对值**（`detect_rarity_by_color`）：

| 等级 | 核心 RGB（实测） | 色相 | 饱和度 | 判据 |
|------|-----------------|------|--------|------|
| S级 | (228,163,12) 金黄 | 42° | 0.96 | 25° ≤ hue ≤ 75° |
| A级 | (210,58,172) 粉紫 | 315° | 0.73 | 280° ≤ hue ≤ 350° |
| B级 | (122,122,122) 灰 | — | 0.00 | sat < 0.25 |

- **核心口径**：先剔近白背景（>200,>200,>200）与近黑边框（<40,<40,<40），
  再只取 `sat>0.55 且 val>0.35` 的笔画中心像素算中位数，抗锯齿边缘不参与。
- **未知色相返回 `?`**（如绿 137°、蓝 240°），落待复核，不硬凑档位。
- ⛔ 旧的 `avg_r > 200` 一类 RGB 绝对阈值已废弃：抗锯齿会把 S 的全均值拉到
  197~199，整批 S 判成 `?`（2026-10-30 实测明音凛/灵可/失纬棋子/质实骰子 5 条全中）。

界面底色：(224,224,226)

## 骰子点数检测（v4新增，v2算法待集成）
通过图像处理检测"投掷点数"列的骰子图标：
- **骰子图标**：RGB(82,83,82)圆角方形底 + RGB(224,224,226)小圆点（点数=1-6）
- **集点赠礼**：无骰子图标，显示"集点赠礼"文字，RGB(74,74,74)
- **返回值**：1-6=点数, 0=集点赠礼, -1=未识别, -2=沉眠地（采集阶段内部信号，清洗时归为 dice_points=0 + action="沉眠地"）

### 骰子图标位置与尺寸（关键事实）
> ⚠️ 下面所有像素值都是在 **2560×1440** 样本图上量的（`test_samples/`）。窗口尺寸或 DPI
> 一变就整体失效（2026-10-30 实测：窗口 1938 宽时骰子实际中心 x≈462，旧的固定 610 完全
> 没覆盖到）。运行时由 `detect_layout()` 自适应：**骰子列中心优先取表头「投掷点数」的
> bbox 中心**，表头没识别出来时按 `scale = 截图宽/2560` 缩放；尺寸、容差、裁切半宽全部乘 scale。

- **骰子中心 x = 610**（2560 基准；实测表头锚点 618.5，两者差 8px 但都覆盖骰子）
- **骰子尺寸 = 53×53**（固定，min=max=53，宽高比≈1.0）
- **骰子 bbox**: x ∈ [584, 636]，y ∈ [name_cy-21, name_cy+52]
- **骰子相对 name 的位置**：x 方向偏移约 -380（骰子在 name 左侧），y 方向偏移 +5~+26（骰子在 name 下方约半个 name_h）
- **骰子间距约 80 像素**（相邻记录的骰子 y 间距），与 name 行间距相近
- **首页自检**：第 1 页会打印 `布局自检: 骰子列=表头锚点 x=... 本页点数未识别 N/M`；
  整页全部未识别时直接告警「骰子列定位可能失效」，不再静默产出一屏 -1

### v1 算法（当前 yihuan_gacha.py 使用）
1. OCR检查"集点赠礼"/"沉眠地"文字 → dice=0/-2
2. 区分骰子底色(G通道略高)和赠礼文字(RGB几乎相等)
3. 找骰子底色最大连通域→包围盒
4. 在包围盒内部找亮色像素→连通域计数
5. 过滤<30px噪点，剩余=点数(1-6)
- **裁切区域**：中心 (629, name_cy)，half_w=name_h*1.9, half_h=name_h*0.9 → y 范围 [name_cy-30, name_cy+30]

### v1 已知缺陷（2026-07-09 发现）
- **y 裁切范围太窄**：v1 的 y 范围 [name_cy-30, name_cy+30]，但骰子实际 y 范围 [name_cy-21, name_cy+52]
- **截断骰子下半部分**：当 y_off 较大时（+20~+26），骰子下半部分（name_cy+30 到 name_cy+52）被截断
- **导致点数偏少**：下半部分的点丢失，v1 数出的点数 < 实际点数
- **影响范围**：5 张样本图 25 条记录中，8 条 v1 点数偏少（v1=3 应为 5、v1=4 应为 6、v1=2 应为 4、v1=1 应为 2 等）

### v2 算法（已验证正确，待集成到 yihuan_gacha.py）
算法文件：`tools/yihuan_gacha/detect_dice_v2.py`
1. OCR检查"集点赠礼"/"沉眠地"文字 → dice=0/-2
2. **定向裁切**：x 围绕 610（±40），y 围绕 name_cy（-0.5*name_h ~ +1.5*name_h）
   - y 搜索范围 2*name_h ≈ 70 < 骰子间距 80，不会匹配到相邻骰子
3. **强约束筛选**封闭圆角方形：尺寸 45-60、宽高比 0.8-1.2、填充率>0.5、cx 在 [595,625]
4. 选 y 偏移最接近 name_h*0.5 的候选
5. 在骰子内部找亮色点→连通域计数→过滤<30px噪点

### dot_sizes 模式（点数判定依据，25/25 稳定）
每个点数有独特的连通域大小模式，大点(≥30px)数量=点数：
| 点数 | dot_sizes 模式 | 大点数 |
|------|---------------|--------|
| 6 | `[10,15,66,66,64,64,66,66,21,16]` | 6 |
| 5 | `[10,15,61,61,61,61,61,21,16]` | 5 |
| 4 | `[10,15,61,61,61,61,21,16]` | 4 |
| 3 | `[10,16,67,70,67,22,16]` | 3 |
| 2 | `[10,15,61,61,21,16]` | 2 |
| 1 | `[10,16,164,22,16]` | 1（单个大圆点 164px） |

### VL 验证结果（2026-07-09）
用 ModelScope Qwen3-VL-235B 验证 4 个 case，全部支持 v2：
- 笑口常开：v1=6, v2=6, VL=6 ✓
- 真红：v1=5, v2=5, VL=5 ✓

## 集点赠礼机制
每10次投掷，无论点数结果，额外赠送一个A级道具，此时投掷点数列显示"集点赠礼"。

## 沉眠地机制
限定棋盘中的特殊投掷方式，投掷点数列显示"沉眠地"文字而非骰子图标，产出大量失纬棋子（通常30个）。与集点赠礼同属额外奖励类（`dice_points=0`），通过 `action="沉眠地"` 区分，供模拟器统一处理。

## JSON 格式
每条记录：
```json
{
  "action": "掷骰|集点赠礼|沉眠地",
  "type": "角色|弧盘|滑翔翼|道具",
  "name": "浔|「电音」狂欢|幽兰|...",
  "rarity": "S|A|B",
  "count": 1,
  "dice_points": 3,
  "time": 1778398596
}
```
- `dice_points`: 1-6=掷骰点数, 0=额外奖励(集点赠礼/沉眠地), -1=未识别
- `action`: 区分 `集点赠礼` 与 `沉眠地`（两者 `dice_points` 均为 0，供模拟器统一处理）
- `time`: Unix时间戳（UTC 1970-01-01起的秒数），缺失为0
- 按棋盘类型分组：`限定棋盘` / `标准棋盘`

### 弧盘研募池记录格式
武器池记录与角色池同库存储（`yihuan_gacha_database.json` 的 `弧盘研募` 键），但字段略有差异：
```json
{
  "action": "抽卡",
  "type": "弧盘",
  "name": "众人追寻之物|拔刀|勿忘伞|...",
  "rarity": "S|A|B",
  "count": 1,
  "dice_points": -1,
  "time": 1778398596,
  "research_type": "奇迹盒盒"
}
```
- `action`: 固定为 `抽卡`（武器池无掷骰/集点赠礼机制）
- `type`: 固定为 `弧盘`（武器池物品全是弧盘）
- `dice_points`: 固定为 `-1`（武器池无骰子）
- `research_type`: 研募类型，目前都是 `奇迹盒盒`，仅作存储，不影响其他数据。未来若出现其他类型再追加功能
- 名称存储时**不带** `弧盘·` 前缀（OCR 直接读取名称列），清洗脚本会自动补前缀后查 RARITY_MAP

## 工作流程

### 1. 采集数据
```bash
uv run python workspace/yihuan_gacha/yihuan_gacha.py    # 采集所有棋盘
```

**调试模式**（2026-08-26 加入）：设 `YIYUAN_DEBUG=1` 环境变量后每步打印截图/OCR 耗时；脚本默认行缓冲输出（后台运行也实时可见），OCR 请求带 180s 超时防后端挂死时永久阻塞：
```powershell
$env:YIYUAN_DEBUG = "1"; .venv\Scripts\python.exe workspace/yihuan_gacha/yihuan_gacha.py
```

> ⚠️ 后端依赖：OCR 推理设备由 `config.toml [models] paddle_device` 控制。2026-08-26 曾实测 paddlepaddle-gpu 3.2.2 在新 NVIDIA 驱动上 GPU 推理挂死后端；2026-09-30 复测 `paddle_device = gpu` 已可用（单页 OCR 5-14s，全程 130+ 页无挂死），AGENTS.md 技术栈亦以 GPU 为准。**若**采集卡在"开始收集"且后端无响应，再检查该项是否被改成 `gpu`/`auto`，必要时临时回 `cpu`。

**采集步骤：**
1. 确保异环游戏打开，抽卡统计页面可见
2. 脚本自动申请屏幕控制授权（弹窗批准一次即可；点击中途 403 也会自动重新申请）
3. 脚本自动截图→OCR→翻页→记录
4. 翻页时不需要确认（`require_confirm=False`）
5. 采集完成后先保存不可变原始数据到 `raw/` 目录，再增量合并到 `yihuan_gacha_summary.json`

**可靠性机制（v4+）：**
- 页码跟踪：记录已读页码，检测翻页是否真正生效
- 重复检测：如果翻页后页码未变化，自动重试
- 翻页重试（v5+）：每次翻页最多重试5次，每次重试重新截图找按钮位置，验证页码变化
- 棋盘切换重试（v5+）：切换棋盘最多重试5次，多次点击确保下拉框打开，切换后多次验证是否成功
- 棋盘类型验证（v5+）：`collect_board` 开头验证当前棋盘类型是否匹配目标，防止切换失败但页码恰好为1时收集错误数据
- 连续失败保护：翻页彻底失败后停止，避免死循环
- 颜色稀有度检测：通过裁切文本区域像素判断 S/A/B 稀有度
- 骰子点数检测（v4新增）：图像处理检测骰子图标中的亮色圆点数量
- 数量提取（v5修复）：正确识别行文本中的独立整数作为数量，支持名称末尾粘着数字的OCR合并情况

**采集性能（2026-10-30 起，每页 6.5s → 约 3.8s）：**
- 单页耗时构成（1938×1127 窗口、CPU OCR）：OCR 4.3s + 解析 0.18s + 点击/等刷新/截图 2.0s
- **流水线翻页**（`iter_pages_pipelined`）：上一张截图的 OCR 与「点下一页 + 等刷新 + 截图」重叠。
  点击用上一页 OCR 得到的按钮位置（同一面板跨页稳定）；页码没前进就退回同步重试，
  翻页失败时已截好的新图会先被用掉，不会丢页；OCR 失败会对同一张图重识别一次。
- **面板 ROI**（`learn_page_roi`）：首帧学出内容范围（排除窗口标题栏与两侧背景），
  后续页只送这一块再 OCR，省约 16%。裁剪结果的 bbox 会加回偏移量（实测偏差 0.2~0.7px）；
  缺表头或页码时自动回退全图重识别。
- ⚠️ ROI / 流水线都只是「更快」，正确性判据不变：页码校验、重复检测、失败重试全部保留。

**⚠️ 原始数据保护规则（极其重要！）：**
- **采集完成后立即保存不可变原始数据**，无论数据质量好坏
- 原始数据位置：`workspace/yihuan_gacha/raw/yihuan_gacha_raw_YYYYMMDD_HHMMSS.json`
- 每次采集生成一个带时间戳的文件，**永不覆盖、永不删除**；清洗成功后由 `yihuan_clean.py`
  的 `archive_raw_files()` 统一挪到 `backup/raw/` 归档（同名自动加序号，不覆盖）。归档放在清洗之后，
  因为 `find_latest_raw()` 只认 `raw/` —— 采完就挪走会让清洗读不到原始件
- `find_latest_raw()` 先找 `raw/`，为空再回退 `backup/raw/`，最后才回退 summary
- 本轮没有新记录时不生成 raw 文件（空文件会污染归档）
- 清洗脚本优先从 `raw/` 目录读取最新原始数据，找不到则回退到 summary 工作文件
- **清洗/修正操作只作用于副本**（review/final），绝不修改 raw/ 目录中的文件
- 历史上原始数据因各种清洗/采集/修正处理丢失已达4次，raw/ 目录是最后防线

**十连的时间怎么存（2026-10-30 定，参考鸣潮/方舟/终末地的做法）：**
- 一次十连的 10 条在游戏里**共享同一个时间**（精确到秒，如「2026年10月30日 03:21:31」）。
  库里就这么存，**不做任何单调化**。
- 老版为了拿 `time` 当唯一键，把同组拆成 `t+0 / t+1 / …`（组内最多 +9 秒，实测累计偏移 9~19 秒），
  代价是库里时间**全是假值**：增量水位线、按时间对齐、跨池排序全部失效。2026-10-30 已整体重建。
- 唯一性改由**内容多重集**承担：`(名称, 稀有度, 时间) → 出现次数`，同名同稀有度靠计数区分
  （B 级重名极密，一期里同名 4~5 条很常见）。与 `wuwa_gacha.py` 的 `_record_key` / `Counter` 同构。
- 三家有官方接口的游戏怎么处理十连时间（**没有一家改时间**）：

  | 游戏 | 十连的 10 条 | 唯一性靠 | 增量靠 |
  |---|---|---|---|
  | 明日方舟 | 共享同一 `timestamp`（毫秒） | `pos` 0–9（组内位置） | 复合键 `(poolId, gachaTs, charId, pos)` 合并 |
  | 终末地 | 共享同一 `timestamp` | 全局自增 `seqId`（严格递增） | 游标：库内最大 seqId 作 `stop_seq_id` |
  | 鸣潮 | 共享同一 `time`（秒） | 内容多重集 `Counter` | 同一套多重集增量合并 |

  方舟另有个坑：`official` 来源 487 条**零残缺**，`xhh`（小黑盒导出）1092 条里有 9 组只有 8~9 条、
  `pos` 中间缺位 ⇒ **不能拿「组里不满 10 条」反推「只抽了 9 次」**。
- 字段 `time_source` 标明时间可信度：`raw` = 游戏里读到的真值；`legacy` = 超过游戏 6 个月
  保留期、raw 已永久不可得的旧记录（重建时限定 14 条 / 标准 50 条），时间带历史偏移，只能当排序用。

**增量采集（内容多重集，2026-10-30 起）：**
- 判据 = `PoolMatcher.classify_page()`：库侧建 `Counter((名称, 稀有度, 时间))`，逐页比对时用
  「页内同内容已出现次数 < 库内该内容条数 ⇒ 已采」。**幂等**——翻页失败重读同一页不会重复计数。
- 判停 = **连续 2 页全部已采**才停（记录按时间倒序，再往后只会更旧）；单页全旧不停，
  避免"恰好抽到重复"被误判成到底。
- 时间解析不出来的记录**一律当新记录保留**（宁可多采一条，也不能静默丢卡）。
- 为什么不用「纯时间水位线」：同一次十连跨两轮采集（采到一半断了）时，水位线会把同组剩下的
  记录判成"已采"而丢掉；多重集按条数差额比对，库里 6 条、本轮 10 条 ⇒ 差额 4 条照样收进来。
- 为什么不用「纯名字/纯指纹」：① 只按名字——B 级重名极密，一页 5 条常有同名，会误判成"已采"；
  ② 只按 `(棋盘, 名称, 时间戳)` 指纹——老库时间被单调化过，与 raw 真时间永不相等，恒不命中。
  **名字 + 稀有度 + 时间三者一起**才既分得开又不误杀。名称侧另有 `_norm_name_for_match()`
  统一 OCR 分隔符变体（`弧盘·：「电音」狂欢` → `「电音」狂欢`），否则会白翻好几页。
- 实测（2026-10-30 重建后，库即最新）：弧盘 库260/52 页 → 停第 2 页 0 条新；限定 库479/93 页 →
  停第 2 页；标准 库358/62 页 → 停第 2 页。三池都只跑 2 页。
- `--force` = 跳过判重、全量翻到最后一页（怀疑库缺页时用）。
- ⚠️ 增量 raw 是**片段**不是全量快照；清洗合并靠 `raw_min_time - 120` 切分（早于它的旧库记录
  全部 `preserved` 并标 `time_source=legacy`），所以增量 raw 只增不减，不会把库砍短。
- 需要用历史原始件重算时：`uv run python workspace/yihuan_gacha/yihuan_clean.py --raw <路径>`

**注意事项：**
- 始终使用窗口截图（`mode="window"`），不要全屏
- 采集脚本内部调用后端 API 时传 `format="base64"` 获取图片数据（脚本内部处理，不经过 MCP，不会撑爆上下文）
- 翻页点击坐标来自 OCR 识别的"下一页"位置
- 切换棋盘类型时，点击**当前棋盘名称值**（如"限定棋盘"），而非"棋盘类型"标签
- 下拉框是居中显示的，点击位置要在棋盘名称的中心
- OCR 坐标链路已修复：截图管线关闭 UVDoc，bbox 与窗口截图 1:1 对应（回归误差 1-3px）；禁止恢复旧仿射参数。翻页文字可直接用 OCR bbox 中心定位
- **切换棋盘后游戏自动将页面置1**：如果切换后检测到不在第1页，说明棋盘切换失败，仍在之前的棋盘，应跳过收集避免重复数据
- **坐标必须为整数**：`/screen/action` 的 `x`/`y` 参数类型为 `int`，传浮点数会返回 422 验证错误。脚本中应使用 `int(x)` 转换

**Agent 审查时的截图+OCR 流程（重要！）：**
Agent 需要截图验证游戏画面时（如确认当前在武器池页面），**不要**用 `capture_screen` MCP 工具（`format="info"` 不返回图片数据也不保存文件，`format="base64"` 会撑爆上下文）。正确做法是用 `exec_python` 一步完成截图+OCR：
```python
import requests, base64, os, tempfile
API = 'http://127.0.0.1:8766'
cap = requests.post(f'{API}/screen/capture',
    json={'mode':'window','window_title':'异环','format':'base64'}).json()
img_path = os.path.join(tempfile.gettempdir(), 'yihuan_check.png')
with open(img_path, 'wb') as f: f.write(base64.b64decode(cap['image']))
ocr = requests.post(f'{API}/ocr/path/json', json={'path': img_path}).json()
for it in ocr.get('details', []):
    box = it.get('box', [])
    cx = sum(p[0] for p in box)//len(box) if box else 0
    print(f'cx={cx:5d} text={it.get("text","")!r}')
```
这样只返回 OCR 文本结果到上下文，避免 base64 图片数据污染对话。
- **清洗脚本字段名对应**：采集脚本输出 `time`/`quantity` 字段，清洗脚本读取时需兼容 `date`/`count` 等变体名
- **骰子图标中心x=610**（2560 基准；运行时按表头锚点/分辨率自适应，详见"骰子点数检测"章节）
- **⚠️ 清洗对"本次 raw 里没有的棋盘"是从 `yihuan_gacha_database.json` 保留的**：所以分批采集（先角色池、后武器池）时，必须先把上一批的 review 定档进 database，再跑下一批的清洗，否则该批清洗会用旧库覆盖，丢掉本轮新数据（2026-09-30 实测：武器池单独 raw 清洗时会 `保留已有数据: 限定棋盘 (426条)`，取的就是 database 里的值）
- **⚠️ `yihuan_review.py` 优先读 `database.json`**（`data_file = DATABASE_FILE if exists else REVIEW_FILE`）：清洗刚写完 review、还没定档 database 时跑探查，审的是上一轮的旧数据且不会报错（2026-09-30 实测：review 已 806 条，探查仍报 718 条"未发现异常"）。要么先定档再探查，要么直接对 review.json 自查

### 2. 清洗数据
```bash
uv run python workspace/yihuan_gacha/yihuan_clean.py
```

**清洗规则：**
- 标准化名称格式：`弧盘·xx`、`角色·xx`、`道具·xx`、`滑翔翼·xx`
- 修正OCR错误名称（NAME_FIXES映射表）
- 忽略骰子图标（田、：等OCR噪音）
- 稀有度：RARITY_MAP映射表（权威来源，用户确认过）
- 集点赠礼标记保留（dice_points=0）
- 骰子点数保留（dice_points=1-6）
- **不做去重**：同一秒的十连抽可能产出多条相同记录，是合法数据
- **时间验证**：清洗时自动检查时间不超过当前时间、按OCR顺序单调非递减（允许连续相同时间）
- **名称中混入时间**：OCR有时将时间文字粘到道具名称后面，`clean_name()` 会自动剥离

**⚠️ 清洗原则：不要过度依赖智能正则！**
- 正则只能处理已知模式，无法覆盖所有OCR噪音变体
- 遇到新的OCR错误变体，直接在 `NAME_FIXES` 中添加映射，比写复杂正则更可靠
- 正则负责通用清理（去时间、去噪音字符），具体名称修正靠映射表
- 每次清洗后检查名称清单，发现新变体立即补充映射

**清洗不是一劳永逸！** 新道具/角色会不断出现，需要：
1. 每次清洗后自查名称清单
2. 有疑问的名称问用户确认
3. 确认后更新 RARITY_MAP 和 NAME_FIXES

### 3. 审核流程（两步审核）
1. **AI自查**：清洗脚本输出名称清单，AI检查是否有明显错误
2. **用户审核**：汇总名称清单给用户确认
3. 确认后才写入最终归档

### 3. 探查审核
```bash
uv run python workspace/yihuan_gacha/yihuan_review.py
```
输出统计摘要：物品名称/个数/稀有度、骰子点数分布、集点赠礼占比、异常检测（稀有度?、缺时间、点数占比异常等）。一目了然，无需逐条翻阅。

### 4. 写入最终归档
审核通过后，将 `yihuan_gacha_review.json` 写入 `yihuan_gacha_final.json`。

**增量更新规则：**
- 新采集的数据清洗后，与现有归档合并
- 键是**内容多重集**，不是集合：`(action, type, name, count, time) → 出现次数`，同一条重复出现按次数逐条比对（一次十连里同名同稀有度多条、且共享同一时间，用集合会把它们压成一条 ⇒ 丢卡）
- 已有记录不覆盖；同一十连的 `time` 允许相等，**不要为了"唯一"去改时间**
- 按时间稳定排序（`time=0` 排最后），组内保持采集顺序

### 5. 缺时间记录补全
time=0 的记录需要补全，方法：
1. 根据上下文时间推断大致范围
2. 下次打开游戏时，重新OCR对应页面获取时间
3. 用户可提供 `yyyy年mm月dd日 hh:mm:ss` 格式，脚本自动转Unix时间戳

### 6. 归档后更新记忆（收尾必做）
写入归档后，`POST /memory/yihuan_gacha` 更新采集状态，下次任务开始时读取可接上上下文：
- `updated_at`：本次日期
- `last_collection`：raw 文件名 + 各池条数
- `database_state`：归档文件各池条数
- `key_facts`：本次新确认的物品稀有度、新 OCR 变体、踩过的坑（授权申请方式、paddle_device、loop 任务暂停/恢复）

## 弧盘研募池（武器池）

### 机制说明
- **池名固定**：始终为 `弧盘研募`，不随版本更换，无需切换棋盘
- **普通抽卡**：非棋盘机制，不走格子，直接得到结果
- **保底规则**：
  - 1 研募 = 10 弧盘（即十连抽）
  - 6 研募（60抽）保底 S 级弧盘
  - 8 研募（80抽）保底当期限定 S
  - A 级 1 研募（10抽）保底
  - 保底永久累计，可继承至其他限定特刊
- **出金判定**：武器池物品全是弧盘，故任意 S 级都算出金（`gold_filter_rules.weapon_research.gold_type = "弧盘"`）
- **额外奖励**：S=40 失纬棋子, A=4 失纬棋子, B=20 迷迭棋子
- **研募类型**（`research_type` 字段）：目前都是 `奇迹盒盒`，仅作存储，不影响其他数据

### 界面布局（OCR 采集）
武器池统计页面共三列，无稀有度列（用颜色检测）：
| 列 | 内容 | 2560 基准分界 |
|----|------|------------|
| 名称列 | 弧盘名称（不带 `弧盘·` 前缀） | cx < 1100 |
| 研募类型列 | 研募类型（如 `奇迹盒盒`） | 1100 ≤ cx < 1600 |
| 时间列 | `YYYY年M月D日HH:MM:SS` | cx ≥ 1600 |

> 分界不写死：`weapon_column_bounds()` 取表头「弧盘列表 / 研募类型 / 研募时间」三个
> bbox 中心的相邻中点；表头认不全才退回上表的值 × `截图宽/2560`。

颜色稀有度检测与角色池一致：先查权威表，表里没有才按 HSV 判（S 金黄 42° / A 粉紫 315° / B 灰 sat≈0）。

- 无需切换棋盘（池子只有一个）
- 无骰子点数检测（`dice_points` 固定 `-1`）
- 采集后保存到 `yihuan_gacha_summary.json` 的 `弧盘研募` 键
- 原始数据同样保存到 `raw/` 目录；每翻一页另外增量写 `raw/_partial_weapon.json`（成功结束自动删）

### 清洗
```bash
uv run python workspace/yihuan_gacha/yihuan_clean.py
```
清洗脚本自动检测 `弧盘研募` 键：

- `action` 设为 `抽卡`，`dice_points` 设为 `-1`
- 保留 `research_type` 字段
- **与现有数据库合并**：以 `(action, type, name, count, time, research_type)` 为键去重，保留角色池数据不被覆盖
