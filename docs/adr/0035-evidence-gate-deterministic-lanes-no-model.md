# ue_learning_copilot 证据门：检索与事件流两路刻意不过模型

## Context

`workspace/ue_learning_copilot/`（UE 学习副驾）的产品承诺是"每条事实断言都带**可当场核实**的出处"——用户可以按 `相对路径:行号` 翻开引擎源码亲眼对一遍。这个承诺由 `citations.py` 的证据门机器执行：`PATH_MISSING` / `QUOTE_MISMATCH` / `NOT_IN_EVIDENCE` / `PATH_OUT_OF_ROOT` 四种判红，任何一种都让整份回答不合格。

初版方案是"四条证据路全走 agent"：让 LLM 自己检索源码、读日志、抓网页，再自动挂出处。该方案在 spec 讨论阶段被**明确否决**（用户裁决），代之以当前架构：

- **源码检索路（`retrieval.py`）与事件流路（`logwatch.py`）刻意不过模型**——行号、原文片段全部是确定性检索的产物，LLM 只在最后的综合答题（`answer.py`）里基于证据集写作，且提示词硬约束"只允许引用本轮证据标号"，越界引用被证据门打回。
- **网页路（`web_lane.py`）不过模型做选页**，匹配/选页/抽片段全在本地做；URL 出处走独立的 `UrlEvidence` 判据（页面正文必须真含引用片段）。
- **模型参与度的边界**：LLM 唯一的产出是"证据集内的综合叙述"，它无法发明出处——发明即判红，非零退出。

这个设计实施后立刻用真机证伪了一次"看起来是模型问题"的现象：T04 端到端首跑判红，根因是**检索**把 8 条证据全花在 `#include`/前置声明上、一条目标 API 都没有——模型按提示词规则正确回答"证据不足"。若检索本身过了模型，这次失败会被掩盖成"模型幻觉"，无从定位。

## Decision

1. **确定性证据路永不过模型**。源码路 / 事件流路的检索、过滤、行号定位全部是代码；LLM 只消费证据集，不生产证据。（唯一例外见下方「例外：查询理解只产检索键」——模型可以在检索**之前**把中文提问翻成英文检索词，但它产的是"去哪儿找"的键，不是"找到的东西"，证据门一字未改。）
2. **证据门是唯一不可让渡的硬门**：无出处的句子自动降级为"未核实"并保留可见标注；引用不存在的标号判红；spec 明写"造不出红则整个项目失去存在理由"（反向验证已过）。
3. **检索缺陷要能被证据门暴露出来**，而不是被模型的流畅叙述掩盖——这是"检索不过模型"的第二重理由：证据集的质量缺陷留下机器可查的痕迹。

## 例外：查询理解只产检索键

`retrieval.py` 与 `web_lane.py` 都用同一条正则 `IDENTIFIER_RE`（`[A-Za-z_][A-Za-z0-9_]{2,}`）从提问里抽英文标识符当焦点词。这带来一个诚实的缺口：**中文提问抽不出任何标识符 → 检索零命中 → 证据门如实判"证据不足"**。这不是幻觉，是可定位的检索盲区（正是 Decision 3 想让门暴露的那类缺陷）。

用户裁决引入一个**受约束的例外**来补这个盲区：`query_expand.py` 在检索**之前**调一次 LLM，把中文提问翻成一组英文检索词（如"角色自己的速度存在哪个字段"→ `ComponentVelocity`、`CharacterMovementComponent`），拼进 `search_query` 再喂给确定性检索路。

它与本 ADR 主命题不冲突，因为红线守的是"证据"而非"查询理解"：

- **模型产的是"去哪儿找"的键，不是"找到的东西"**。扩展词只改变检索的关键词，进入证据集的每一条 hit 仍由确定性代码定位（行号、原文片段、URL 片段），模型无从参与。
- **证据门一字未改**。扩展词把提问翻得再花哨，引用了不存在标号仍判红、出处路径越界仍判红、正文不含引用片段仍判红。最坏情况是扩展词没帮上忙 → 检索依旧零命中 → 诚实的"证据不足"，**绝不会**凭空造出一条带出处的假证据。
- **接缝刻意收窄**：扩展词只进检索，**不进答题 prompt，也不进展示正文**（有回归测试锁定 `ZebraWidget` 这类扩展词不出现在送模型的上下文里）。模型叙述仍只基于证据集写作。
- **触发与失败都有界**：仅当提问含 CJK 字符才扩展（纯英文零额外延迟/配额）；扩展调用失败或模型没给可用词就退回原句检索。单测若注入了答题 `llm` 却没注入 `expand_llm`，直接跳过扩展——避免离线测试误发真网络调用。

换句话说：本 ADR 禁止的是"让模型生产证据"，允许的是"让模型帮忙决定去哪儿找证据"。前者击穿产品承诺，后者只是给检索换了更好的关键词，证据门这层硬约束全程照常把关。

## 三项标准逐项打分（`docs/adr/README.md`）

- **Hard to reverse** ✅ — 反转 = 拆掉 `citations.py` 机器门、两个确定性证据路的结构、146 条测试中的证据门反向验证群，同时推翻 spec 的唯一硬门与"无出处即不合格"的 agent 行为契约。远超"改一个 if-block"。
- **Surprising without context** ✅ — 未来读者会问"LLM 本来就擅长检索，为什么费这么大劲自建 grep？为什么网页选页也不让模型做？为什么明明有一次模型调用却不让它顺手找出处？"——没有本 ADR 的语境，这套结构看起来像对 LLM 能力的不信任式过度工程。
- **Real trade-off** ✅ — 被拒绝的替代方案真实存在且否决理由不显然："四路全 agent"（初案，用户否决）：模型回忆产出的行号不可核实，出处从"可验证的指针"退化为"看起来像引用的文本"，直接击穿产品承诺。代价也真实：检索质量瓶颈从模型转移到代码（焦点词策略、目录优先级排序、截断语义都要手写，T04/T06 各修过一个真检索缺陷），且模型无法用常识弥补检索的盲区——换来的是每条出处可当场核实。

**3/3 通过** ⇒ 成文。

## Consequences

- 证据集质量 = 回答质量的上限。检索侧的可观测性（每路 `strategy/files/elapsed/partial` 全量上报）是必须维持的约束，砍掉它等于砍掉"检索缺陷可定位"这层能力。
- 新增证据路（如屏幕 OCR、官方文档）必须遵守同一契约：进入证据集的每条 hit 自带机器可核实的定位；模型不参与定位。
- 判卷脚本与判红逻辑冻结（spec Anti-Cheat）：认为判据不合理 → 写 `BLOCKED.md`，不改卷子。
